# Стратегия проверки

Это план полной проверки сервиса, не отчёт о production acceptance. Go DTO/mapper, HTTP handler library и внутренняя server composition реализованы и проверяются синтетическими tests; запускаемый `cmd/api` и production recognizer/OCR wiring отсутствуют. Handler проверяет заявленный MIME type и multipart-форму, но не декодирует image bytes. Локальный OCR smoke и ограниченное сравнение алгоритмического прототипа описаны ниже и в [результатах прототипа](OCR_ALGORITHM_RESULTS.md). Согласованного held-out набора для расширенной оценки нет.

## Набор данных и метрики

- Получить разрешение и согласие на набор; определить доступ, минимизацию, хранение, удаление и запрет использования реальных сканов в Git/логах.
- Разделять данные по документам на разработку/настройку параметров обработки и закрытую held-out оценку; изображения одного паспорта не должны пересекать разбиение. Модель не обучается и не дообучается.
- Размечать все 11 полей и случаи неопределённости. Считать exact match по каждому полю и по документу для всех 10 обязательных полей (отчество необязательное).
- Отдельно считать покрытие, ошибки ложного заполнения, пропуски и частоту ручного исправления. Калибровать состояния неопределённости только по данным настройки.
- Проверить целевую матрицу Windows/Linux/macOS на x86_64/arm64 на обычных настольных компьютерах и ноутбуках, не трактуя её как гарантию поддержки любого устройства. Измерить время распознавания и пиковую память на CPU как обязательном базовом режиме, включая поведение при ограниченном параллелизме. Если runtime и оборудование поддерживают GPU/ускорение и оно проверяется, отдельно зафиксировать результаты вместе с точными моделями компьютера, ОС, CPU, RAM, GPU и runtime; определить минимальные версии ОС, CPU и объём RAM по результатам пилота.

## Контракт и интеграция

- При изменении контракта проверять OpenAPI 3.0.3, разрешение refs, все named examples и их точное равенство копиям в [API_RESULT.md](API_RESULT.md); проверять response schema на примерах.
- Проверять обязательность всех 11 field keys, запрет дополнительных ключей, состояния `recognized`/`uncertain`/`missing` и допустимые сочетания `value`/`issues`, включая `uncertain` с `value: null` и conflict issue.
- Проверять, что ограничения значений действуют и на `uncertain`: календарно корректные даты `YYYY-MM-DD`, строковые series/number с ведущими нулями, department code, `M`/`F`, непустые имена и значения без словарных исправлений. Проверять nullable patronymic без вывода фактического отсутствия из `null`.
- Проверять обязательный массив warnings, `{code,message}` для warnings/issues, `no_fields_recognized` при всех-null результате, пустые messages, отсутствие PII и то, что клиенты не разбирают message.
- Проверять, что `ErrImageUnprocessable` recognizer-а даёт `422 image_unprocessable`, а количество пустых полей не даёт `422`; handler сам изображение не декодирует. Проверять безопасный mapping `processing_failed`, `ocr_unavailable` и `processing_timeout`.
- Проверять исправление, очистку, повторное распознавание, ревизии и отбрасывание устаревшего ответа по operation/image/revision.
- Проверять отказные ответы для malformed/duplicate multipart parts, неподдержанного заявленного MIME type, configured upload cap, concurrency cap, cancellation/deadline и typed recognizer errors. LAN composition проверяет bind IP и непустой caller-supplied CIDR allowlist; handler должен отклонять peer вне allowlist до чтения body и semaphore, игнорируя forwarded headers. Дополнительная identity-auth и QPS/rate limit не выбраны и не реализованы.
- Проверять, что временные файлы удаляются при успехе, ошибке и отмене; логи не содержат изображений, распознанного текста или PII.
- Сверить подтверждённый клиентом snapshot с тем, что отображается, считается полным и экспортируется. Формат экспорта остаётся открытым.

## Статус

Для локального этапа подготовлены приватный observations/v1 handoff и comparison runner в [ocr/experiments](../ocr/experiments/README.md). В алгоритмическом прототипе реализованы preprocessing/fallback и Go field-association правила; scorer gender исправлен по enum-формату. Это correction измерения, не качество OCR. На двух development-изображениях C дал 15/20 точных предложений по обязательным полям, все остаются `uncertain` и требуют проверки человеком. Подтверждены 52 Go test cases. Текущий набор составляет 23 Python unit tests (16 region, 3 TSV, 4 runner): прежние 22 прошли, затем focused runner suite из 4 тестов также прошёл. OCR observations переиспользованы, поэтому OCR-время в отчёте историческое; свежий короткий прогон относился к Go post-processing. Полные OCR JSON и поля остаются приватными. Эксперимент не является held-out оценкой, проверкой production API или acceptance качества.

Нативный harness и последовательная локальная обёртка находятся в [ocr/experiments](../ocr/experiments/README.md). Повторный batch `2026-10-28` завершился с кодом 0 и статусом `PASS` для всех трёх входов на обоих движках; SHA-256 артефактов совпали с закреплёнными значениями, RapidOCR использовал только `CPUExecutionProvider`. Parser исправлен через `QUOTE_NONE` и строгую проверку 12 TSV-колонок; три регрессионных теста и `py_compile` прошли, целостность TSV для фото подтверждена. Ограниченный консервативный baseline буквальных совпадений для двух фото приведён в [результатах OCR-пилота](OCR_PILOT_RESULTS.md); это не accuracy и не production acceptance. Экспериментальный Go extractor прошёл локальные проверки, но интеграция в публичный API/runtime не подтверждена; требуется расширенная оценка качества. Среда и диагностические времена описаны в том же документе.

На 2026-10-29 прошла статическая проверка OpenAPI 0.2.0: Python 3.12.14 с `openapi-spec-validator` 0.9.0 (`validate_spec`), `openapi-schema-validator` 0.9.0 (`OAS30Validator` + `FormatChecker`) и PyYAML 6.0.3 duplicate-key check завершились успешно. Все 4 named examples и 4 копии JSON в [API_RESULT.md](API_RESULT.md) совпали; 23 schema cases дали ожидаемый результат (4 положительных, 19 отрицательных), включая отклонение календарно недопустимой даты `2023-02-29`. Это историческая проверка предыдущей версии.

Для OpenAPI 0.3.0 verifier повторно подтвердил `validate_spec`, duplicate-key check, все 4 named examples и их 4 JSON-копии в [API_RESULT.md](API_RESULT.md); 23 schema cases дали ожидаемые результаты. Дополнительно 14 JSON-ответов текущего handler (успехи и ошибки, включая 404/405 fallback) прошли OAS 3.0 schema и format validation; проверены JSON Content-Type и совпадение UUID header/body. Schema по-прежнему сама не выражает all-null warning condition. Это историческая проверка предыдущей версии.

Для Go API slice test-first цикл дал ожидаемый compile RED при отсутствующем `MapExtraction`, затем зелёные mapper tests. Поведенческие RED выявили запись 400 при отменённой загрузке (ожидалось ноль записей) и чтение тела неожиданной multipart-части до её отклонения; handler исправлен так, что cancellation не пишет ответ, а unexpected part отклоняется до чтения его тела. Проверка chunked multipart epilogue подтверждает сохранение 413 при превышении общего body bound. После streaming rewrite прошли `go test ./internal/httpapi -count=1`, независимый `go test -race ./...` и `go vet ./...`; на тот момент race suite включала 14 top-level tests в `internal/api` и 23 в `internal/httpapi` (table cases отдельно не пересчитывались). Эти проверки используют синтетические fixtures и test recognizers.

Поведенческий тест multipart загрузки проверяет, что `Recognizer` получает содержимое файла для binary part без `Content-Transfer-Encoding` и для quoted-printable part после снятия transfer encoding. Оба варианта используют одинаковые исходные file bytes, включая `=41`, CRLF и байт вне ASCII; это тест передачи содержимого file part, а не wire-представления.

Для внутренней композиции `internal/server` synthetic tests покрывают runtime limits и арифметические границы, HTTP маршрут с injected recognizer, bind error, pre-cancel и startup/cancellation race, single-use, владение listener, graceful drain, forced close по shutdown timeout, unexpected Accept error, header/body timeouts, `Run(nil)`, nil listener/context в `Serve`, и отсутствие утечки recognizer panic sentinel в ответ/стандартный лог. Последняя проверка относится только к synthetic recognizer-у. Из-за поведения Go `net/http` при транспортном закрытии raw TCP fixtures закрывают client conn до остановки; для 431/body timeout shutdown budget больше наблюдённого 500 ms RST linger.

В предыдущей проверке server composition прошли `go test ./internal/server -count=1 -timeout=25s -v` и focused privacy/header-overflow tests. Независимая проверка прошла `go test -race ./... -count=1` (Go 1.27.1; `internal/server` 3.161 s; все пакеты, включая `cmd/ocr-eval`, без ошибок) и `go vet ./...` (exit 0). В том тестовом срезе было 15 top-level test functions `internal/server` без учёта table subtests. Проверки используют synthetic data и injected test recognizers и не являются production acceptance.

LAN-срез добавил correlated `403 access_denied`, проверку числового прямого `RemoteAddr`, игнорирование forwarded headers, ранний отказ до semaphore/body, нормализацию/копирование CIDR, проверку bind address при `New` и actual TCP listener при `Serve`. LAN-срез проверялся focused LAN-тестами и полным набором двух пакетов. После исправлений зон для IPv4-mapped IPv6 адресов прошли focused remote-address table test `go test ./internal/httpapi -run TestRecognizeLANUsesRemoteAddrAndIgnoresForwardedHeaders -count=1`, финальные `go test -race ./... -count=1` и `go vet ./...`. В этих пакетах 8 новых top-level LAN-тестов (4 в `internal/httpapi`, 4 в `internal/server`); всего 28 top-level test functions в `internal/httpapi` и 19 в `internal/server`, без table subtests. Listener integration тесты используют loopback, а public/wildcard listener addresses представлены fake listeners; реальное Android-подключение из LAN и deployment не проверялись.

Статическая проверка OpenAPI 0.4.0 прошла: YAML/duplicate-key validation, `validate_spec`, 4 named examples и их 4 JSON-копии в API_RESULT совпали, 23 schema cases прошли. Отдельные фактические HTTP 403 и 200 JSON-ответы текущего handler прошли OAS 3.0 `OAS30Validator` и `FormatChecker`, включая UUID header/body и `access_denied` code/message. Эти тесты подтверждают package-level mapping, multipart handling, safe static responses, size/concurrency bounds, LAN CIDR admission, server lifecycle, cancellation и timeout handoff; они не подтверждают реальное декодирование изображения, работу production recognizer, OCR latency/quality, cleanup/runtime logs внутри recognizer-а, Android integration, реальную LAN-связность или deploy acceptance. Production recognizer wiring явно отложен пользователем; runnable `cmd/api`, identity-auth/rate policy, TLS/deployment и production limits также не реализованы. Held-out OCR набор не подготовлен.
