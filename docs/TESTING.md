# Стратегия проверки

Это план расширенной проверки качества и развёртывания. Текущий `cmd/api` запускает единственный RussianDocsOCR provider; прежние результаты full auto-VL, unit/process tests и native acceptance ниже относятся к удалённому production route и не проверяют текущую конфигурацию. Они не заменяют held-out evaluation, Android integration или production acceptance. Согласованного held-out набора нет.

## Набор данных и метрики

- Получить разрешение и согласие на набор; определить доступ, минимизацию, хранение, удаление и запрет использования реальных сканов в Git/логах.
- Разделять данные по документам на разработку/настройку параметров обработки и закрытую held-out оценку; изображения одного паспорта не должны пересекать разбиение. Модель не обучается и не дообучается.
- Размечать все 11 полей и случаи неопределённости. Считать exact match по каждому полю и по документу для всех 10 обязательных полей (отчество необязательное).
- Отдельно считать покрытие, ошибки ложного заполнения, пропуски и частоту ручного исправления. Калибровать состояния неопределённости только по данным настройки.
- Проверить целевую матрицу Windows/Linux/macOS на x86_64/arm64 на обычных настольных компьютерах и ноутбуках, не трактуя её как гарантию поддержки любого устройства. Измерить время распознавания и пиковую память на CPU как обязательном базовом режиме, включая поведение при ограниченном параллелизме. Если runtime и оборудование поддерживают GPU/ускорение и оно проверяется, отдельно зафиксировать результаты вместе с точными моделями компьютера, ОС, CPU, RAM, GPU и runtime; определить минимальные версии ОС, CPU и объём RAM по результатам пилота.

## Контракт и интеграция

- Для OpenAPI 0.5.0 проверять, что `GET /v1/stats` отвечает тем же request-ID envelope, требует ту же прямую peer ACL, исключает arbitrary labels/PII, и документирует только cumulative агрегаты. Проверять фиксированные status/error/stage cardinalities, 16 cumulative duration buckets и статический `503 statistics_unavailable`; recognition contract/examples должны остаться неизменными.
- Для `internal/metrics` проверять atomic persistence после каждой observation, reload с cumulative totals, строгую схему и pipeline pin, exclusive process lock, private permissions, fixed closed label sets, overflow rejection и failure health event без raw filesystem details. Перезапуск подтверждает агрегатную персистентность, но не crash exactly-once semantics.
- Для CLI проверять обязательный `metrics.state_path`, config-relative resolution, collision rejection относительно log/lock/backups и `ocr.work_root`, открытие store до provider/server и shutdown после server/provider, до log sink.

## Фактическая metrics acceptance 2026-10-30

Выполненные финальные проверки для metrics slice: `go test -race ./... -count=1`, `go vet ./...`, 22 Python worker unit tests, strict OpenAPI 3.0.3 validation с проверкой duplicate YAML keys и stats-schema positive/unknown-key cases, `gofmt`, diff whitespace check и CLI build прошли. `TestFullPipelineHTTPIntegration` прошёл в пакете `internal/ocr`, который занял `65.042 s`: HTTP `200`, один completed OCR job, четыре completed stage observations, histogram observations и stats poll без прибавления HTTP total. `65.042 s` — package test runtime, не latency или SLO.

Отдельный restart smoke для собранного CLI запустил два последовательных процесса на случайных loopback ports. Один synthetic invalid-JPEG запрос вернул `422 image_unprocessable`; после завершения первого процесса второй загрузил сохранённый state с теми же cumulative totals. Итоговые значения: `http_total=1`, `http_422=1`, `ocr_failed=1`; stats polls исключены из HTTP counters, persistence healthy, state permissions `0700/0600`. Smoke также подтвердил request-ID envelope. Он не запускал полный OCR на этом synthetic JPEG.

После этого 2026-10-30 локальный LAN-процесс был активирован с новым metrics state и проверен read-only и двумя same-host `GET /v1/stats` запросами. Затем один synthetic invalid-JPEG POST дал `http.total=1`, `http.errors=1`, `by_status[422]=1`, `ocr.total=1`, `ocr.failed=1`, `by_error_code.image_unprocessable=1`; последующие stats polls не увеличили счётчики. `persistence.healthy=true`, новый `since` сохранён. Operational log связал HTTP completion и OCR failure по request ID. Это same-host проверка существующего LAN listener и его ACL пути; отдельное устройство Android не подключалось. Identity auth и TLS не добавлялись.

- При изменении контракта проверять OpenAPI 3.0.3, разрешение refs, все named examples и их точное равенство копиям в [API_RESULT.md](API_RESULT.md); проверять response schema на примерах.
- Проверять обязательность всех 11 field keys, запрет дополнительных ключей, состояния `recognized`/`uncertain`/`missing` и допустимые сочетания `value`/`issues`, включая `uncertain` с `value: null` и conflict issue.
- Проверять, что ограничения значений действуют и на `uncertain`: календарно корректные даты `YYYY-MM-DD`, строковые series/number с ведущими нулями, department code, `M`/`F`, непустые имена и значения без словарных исправлений. Проверять nullable patronymic без вывода фактического отсутствия из `null`.
- Проверять обязательный массив warnings, `{code,message}` для warnings/issues, `no_fields_recognized` при всех-null результате, пустые messages, отсутствие PII и то, что клиенты не разбирают message.
- Проверять, что `ErrImageUnprocessable` recognizer-а даёт `422 image_unprocessable`, а количество пустых полей не даёт `422`; handler сам изображение не декодирует. Проверять безопасный mapping `processing_failed`, `ocr_unavailable` и `processing_timeout`.
- Проверять исправление, очистку, повторное распознавание, ревизии и отбрасывание устаревшего ответа по operation/image/revision.
- Проверять отказные ответы для malformed/duplicate multipart parts, неподдержанного заявленного MIME type, configured upload cap, concurrency cap, cancellation/deadline и typed recognizer errors. LAN composition проверяет bind IP и непустой caller-supplied CIDR allowlist; handler должен отклонять peer вне allowlist до чтения body и semaphore, игнорируя forwarded headers. Дополнительная identity-auth и QPS/rate limit не выбраны и не реализованы.
- Проверять, что временные файлы удаляются при успехе, ошибке и отмене; логи не содержат изображений, распознанного текста или PII.
- Сверить подтверждённый клиентом snapshot с тем, что отображается, считается полным и экспортируется. Формат экспорта остаётся открытым.

## Operational logging и OCR telemetry

Перед deployment проверить logging slice на synthetic data. Этот список — acceptance plan; сам по себе он не означает, что проверки уже выполнялись:

- Проверить обязательные `logging.path`, `level`, `max_size_bytes`, `max_backups`; отказ на неизвестном level, слишком малом/отрицательном size и недопустимом числе backups. Относительный log path должен разрешаться от config directory.
- Проверить приватность каталога `0700`, файлов `0600`, отказ на symlink, небезопасные существующие файлы, превышение размера при старте и backups вне retention. Rotation должна удерживать не больше current + настроенного числа backups, каждый не больше `max_size_bytes`; конкурентный второй `Open` одного пути должен безопасно отказать, а конкурентные записи одного sink оставаться валидным JSONL.
- Через реальный `telemetry.Open` проверить safe handler: только фиксированные service/event/component/request/HTTP/stage/error поля; unknown attrs, groups, dynamic message, filenames, query/header/client address, image bytes, OCR text, hashes и exception values не должны появляться в файле. Смоделировать write/rotation failure и проверить один static fallback record без сырого error.
- Проверить panic boundary HTTP handler: неизвестный panic value не отражается в response/log, фиксируются `http.request.panic` и ровно один terminal record `internal_panic`; до commit headers ожидаются `status=0`/`response_bytes=0` и отсутствие synthetic 500. Явный `http.ErrAbortHandler` должен получить один terminal `request_aborted` record и быть повторно передан HTTP server.
- Проверить HTTP request correlation для generated, lowercase, uppercase и mixed-case допустимого UUID: исходная UUID-строка должна присутствовать в header/body, recognizer context, OCR job и worker telemetry. Проверить только нормализованный `unmatched` route и `OTHER` method для неизвестных значений.
- Проверить JSONL telemetry `passport-api-telemetry/v1`: ровно шесть keys, фиксированные enums, четыре этапа в порядке `ocr` → `baseline` → `vl` → `extract`, request ID совпадает с job. Duplicate/unknown keys, malformed/truncated/oversized lines, oversized stream, bad order и request ID mismatch должны вести к максимум одному safe `ocr.telemetry.rejected`, без сохранения worker строки и без изменения OCR результата.
- Проверить, что `stage_completed` означает только exit code 0 соответствующей команды, а `ocr.job.completed` появляется только после private status/artifact/extraction validation и cleanup. Ошибка output validation, cleanup failure, startup failure, cancellation/deadline или timeout должны завершить job безопасным `ocr.job.failed`; process-level stage events не должны сами свидетельствовать об успешном job.
- Проверить stdout `write`/`flush` failure на worker: OCR outcome не должен меняться и raw stderr fallback не допускается. `KeyboardInterrupt`/другой `BaseException` от pipeline runner должен сохранять interrupt semantics, не превращаться в `pipeline_failed` и не выдавать ложный `stage_failed`.

Проверки, уже выполненные для текущего logging slice: `go test -race ./...` и `go vet ./...` прошли; Python bridge suite (22 tests) и выбранные Python tests прошли; после добавления `error_code=ok` для HTTP 200 прошёл uncached race-набор четырёх API-пакетов. CLI был собран, а smoke проверил четыре HTTP status cases. Финальный `TestFullPipelineHTTPIntegration` также прошёл: HTTP 200, UUID совпал в request/response header и body, 11 коррелированных JSONL records (8 process-stage, 2 OCR job, 1 HTTP completion), 6/6 ROI прочитано, 11 публичных field keys с `review_required=true`, workspace удалён; integration test занял 54.79 s, пакет — 55.684 s. Это длительности тестового выполнения, не HTTP duration. Проверка использовала один приватный input на одном macOS host; она не является held-out OCR оценкой или доказательством активации сервиса. Результат не покрывает каждый пункт общего synthetic acceptance списка выше.

После этого отдельно проверен живой локальный `cmd/api`: startup event, HTTP 405 и 422 completion, а для 422 — совпадающий request ID у HTTP completion и `ocr.job.failed`; оба HTTP records содержали ожидаемые статические error codes. Каталог/file log имели modes `0700`/`0600`, worker workspace после probes был пуст. Это same-host проверка запущенного процесса, не Android/remote-device acceptance.

## Статус

Для локального этапа подготовлены приватный observations/v1 handoff и comparison runner в [ocr/experiments](../ocr/experiments/README.md). В алгоритмическом прототипе реализованы preprocessing/fallback и Go field-association правила; scorer gender исправлен по enum-формату. Это correction измерения, не качество OCR. На двух development-изображениях C дал 15/20 точных предложений по обязательным полям, все остаются `uncertain` и требуют проверки человеком. Подтверждены 52 Go test cases. Текущий набор составляет 23 Python unit tests (16 region, 3 TSV, 4 runner): прежние 22 прошли, затем focused runner suite из 4 тестов также прошёл. OCR observations переиспользованы, поэтому OCR-время в отчёте историческое; свежий короткий прогон относился к Go post-processing. Полные OCR JSON и поля остаются приватными. Эксперимент не является held-out оценкой, проверкой production API или acceptance качества.

Ниже приведены архивные проверки исследовательских harness, выполненные до удаления старого Go evaluator. Их результаты не характеризуют текущий RussianDocsOCR provider и не являются production acceptance. Ограниченный baseline буквальных совпадений для двух фото приведён в [результатах OCR-пилота](OCR_PILOT_RESULTS.md); это не accuracy.

На 2026-10-29 прошла статическая проверка OpenAPI 0.2.0: Python 3.12.14 с `openapi-spec-validator` 0.9.0 (`validate_spec`), `openapi-schema-validator` 0.9.0 (`OAS30Validator` + `FormatChecker`) и PyYAML 6.0.3 duplicate-key check завершились успешно. Все 4 named examples и 4 копии JSON в [API_RESULT.md](API_RESULT.md) совпали; 23 schema cases дали ожидаемый результат (4 положительных, 19 отрицательных), включая отклонение календарно недопустимой даты `2023-02-29`. Это историческая проверка предыдущей версии.

Для OpenAPI 0.3.0 verifier повторно подтвердил `validate_spec`, duplicate-key check, все 4 named examples и их 4 JSON-копии в [API_RESULT.md](API_RESULT.md); 23 schema cases дали ожидаемые результаты. Дополнительно 14 JSON-ответов текущего handler (успехи и ошибки, включая 404/405 fallback) прошли OAS 3.0 schema и format validation; проверены JSON Content-Type и совпадение UUID header/body. Schema по-прежнему сама не выражает all-null warning condition. Это историческая проверка предыдущей версии.

Для Go API slice test-first цикл дал ожидаемый compile RED при отсутствующем `MapExtraction`, затем зелёные mapper tests. Поведенческие RED выявили запись 400 при отменённой загрузке (ожидалось ноль записей) и чтение тела неожиданной multipart-части до её отклонения; handler исправлен так, что cancellation не пишет ответ, а unexpected part отклоняется до чтения его тела. Проверка chunked multipart epilogue подтверждает сохранение 413 при превышении общего body bound. После streaming rewrite прошли `go test ./internal/httpapi -count=1`, независимый `go test -race ./...` и `go vet ./...`; на тот момент race suite включала 14 top-level tests в `internal/api` и 23 в `internal/httpapi` (table cases отдельно не пересчитывались). Эти проверки используют синтетические fixtures и test recognizers.

Поведенческий тест multipart загрузки проверяет, что `Recognizer` получает содержимое файла для binary part без `Content-Transfer-Encoding` и для quoted-printable part после снятия transfer encoding. Оба варианта используют одинаковые исходные file bytes, включая `=41`, CRLF и байт вне ASCII; это тест передачи содержимого file part, а не wire-представления.

Для внутренней композиции `internal/server` synthetic tests покрывают runtime limits и арифметические границы, HTTP маршрут с injected recognizer, bind error, pre-cancel и startup/cancellation race, single-use, владение listener, graceful drain, forced close по shutdown timeout, unexpected Accept error, header/body timeouts, `Run(nil)`, nil listener/context в `Serve`, и отсутствие утечки recognizer panic sentinel в ответ/стандартный лог. Последняя проверка относится только к synthetic recognizer-у. Из-за поведения Go `net/http` при транспортном закрытии raw TCP fixtures закрывают client conn до остановки; для 431/body timeout shutdown budget больше наблюдённого 500 ms RST linger.

Архивная проверка старой версии server composition прошла `go test ./internal/server -count=1 -timeout=25s -v`, `go test -race ./... -count=1` и `go vet ./...` (Go 1.27.1; на тот момент в набор входил `cmd/ocr-eval`, теперь удалённый). Она использовала synthetic data и injected test recognizers и не является проверкой текущего RussianDocsOCR provider.

LAN-срез добавил correlated `403 access_denied`, проверку числового прямого `RemoteAddr`, игнорирование forwarded headers, ранний отказ до semaphore/body, нормализацию/копирование CIDR, проверку bind address при `New` и actual TCP listener при `Serve`. LAN-срез проверялся focused LAN-тестами и полным набором двух пакетов. После исправлений зон для IPv4-mapped IPv6 адресов прошли focused remote-address table test `go test ./internal/httpapi -run TestRecognizeLANUsesRemoteAddrAndIgnoresForwardedHeaders -count=1`, финальные `go test -race ./... -count=1` и `go vet ./...`. В этих пакетах 8 новых top-level LAN-тестов (4 в `internal/httpapi`, 4 в `internal/server`); всего 28 top-level test functions в `internal/httpapi` и 19 в `internal/server`, без table subtests. Listener integration тесты используют loopback, а public/wildcard listener addresses представлены fake listeners; реальное Android-подключение из LAN и deployment не проверялись.

## Историческая acceptance прежнего full auto-VL runtime

Model-free Go tests охватывают provider config, private CLI protocol, duplicate/unknown/trailing JSON rejection, upload/output bounds, image ID/hash/extraction binding, error mapping, cancellation/deadline, process-group termination и `Close` cleanup. Model-free bridge suite проверяет передачу полного pipeline через injected process runner; Python модели в этих тестах не загружаются. Финальные проверки после добавления integration helper: `go test -race ./... -count=1` и `go vet ./...` завершились успешно; Python bridge suite — 14 tests PASS. API binaries собраны для macOS, Linux amd64 и Windows amd64; cross-build не является runtime acceptance.

`TestFullPipelineHTTPIntegration` прошёл на macOS CPU с одним приватным изображением: фактический multipart HTTP `200`, UUID совпал в request/response header и body, все 4 pipeline phases completed, registration accepted, 6/6 planned ROI прочитаны (`ok=6`, `empty=0`, `error=0`), PaddleOCR-VL 1.6 native CPU, ответ содержит 11 обязательных field keys и `review_required=true`, private workspace удалён. Связанный logging assertion прошёл для 11 JSONL records: 8 process-stage, 2 OCR job и 1 HTTP completion с тем же UUID. Integration test занял 54.79 s; пакет — 55.684 s. Это времена тестового выполнения, не HTTP duration, benchmark, SLO или оценка точности. Значения полей, источник, image hash и путь к приватному снимку не публикуются.

Отдельный smoke проверил настоящий `cmd/api` LAN процесс на настроенном хостовом интерфейсе: запрос с заведомо некорректным JPEG вернул `422 image_unprocessable`, `X-Request-ID` совпал с UUID в ответе, job workspace остался пустым, runtime log не содержал вывода. Это проверяет запускаемый process, TCP bind, error mapping и rejection cleanup на той же машине; не является Android/remote-device acceptance или успешной OCR-операцией. Проверенные модели и полноценное изображение через public CLI в рамках этой пробы не публикуются.

Native inference подтверждён только на macOS CPU. Linux binary только собран; Linux native OCR не запускался. Windows binary также собран, но provider на Windows fail-closed возвращает `ErrUnavailable`. GPU, held-out документы, Android client, удалённое LAN подключение, общая accuracy, пиковая память и долгосрочная стабильность не подтверждены. Текущая локальная acceptance и повторные команды приведены в [OCR API runtime runbook](OCR_API_RUNTIME.md).
