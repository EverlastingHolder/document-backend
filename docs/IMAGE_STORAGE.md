# Private image storage

`internal/imagestore` is a filesystem foundation used by the asynchronous job-intake service. Neither package is wired into the current `cmd/api`: the synchronous endpoint still processes its upload in the existing private OCR workspace, and the planned async `202` route is not implemented. A successful image-store write alone does not represent an accepted job.

## Interface

The caller creates the store with `imagestore.New(Config{Root, MaxBytes, MaxTotalBytes})`. `Root` and positive `MaxBytes` are required; neither per-object size nor the optional total-volume budget has a product default. `MaxTotalBytes=0` leaves legacy callers unlimited, while asynchronous composition must set a positive value. A configured budget returns `ErrCapacityExceeded` when the next write would exceed it. The store returns fixed sentinel errors for invalid configuration/input, size overflow, invalid or missing keys/objects, collisions, capacity exhaustion, and storage failures. Filesystem details are not included in these errors.

`Store.Put(ctx, data, mediaType)` accepts non-empty bytes and a declared `image/jpeg`, `image/png`, or `image/webp` media type. It parses the media type, lowercases it, and removes optional parameters. It enforces `MaxBytes` against the exact byte length. It does not decode the bytes, prove that they match the declared media type, or apply the recognizer's pixel limits; those checks remain the recognizer's responsibility.

On success, `Put` returns `Metadata` containing a random opaque UUIDv4 object key, SHA-256 digest, byte size, and normalized declared media type. This key is generated independently from the job UUID. The digest and key are internal metadata. Do not place them in public responses, RabbitMQ messages, logs, or metric labels. The key is an object reference, not a public job identifier.

`Store.Open(ctx, key)` accepts only the generated key format, opens a read-only regular object, and rejects missing, malformed, symlink, or otherwise unsafe object paths. The returned `*os.File` must be closed by the caller. `Store.Close()` releases the rooted directory handle and may be called more than once.

`Store.DeleteUploaded(ctx, metadata)` is intentionally narrow. It removes only metadata returned by `Put` on the same live `Store`, only if the public metadata is unchanged, the key still names the original inode, and a bounded read confirms the bytes still match the original size and SHA-256. This protects against forged/changed handles and replacement or in-place mutation; it assumes the root is private and has no concurrent external writers. Its intended use is an upload that the caller has positively determined lost an idempotency race. It is not a general key-based delete or a safe response to an ambiguous database commit.

## Filesystem protections and durability

The configured root must be a directory with mode `0700`; an existing root with different permissions or a symlink at the root path is rejected. When creating a missing root path, the store makes each missing directory private and syncs it and its parent; it does not chmod or remove existing ancestors. The root is held through Go's rooted filesystem API so object operations stay within it. Symlinked ancestors of the configured root are resolved when the store opens. New object files use mode `0600`. These modes restrict access through the configured filesystem permissions; the package does not encrypt image bytes at rest or control mount permissions in a future container deployment.

`Put` writes in bounded chunks to an exclusive temporary file, syncs the file, then hard-links it to its generated key so an existing key is never overwritten. It removes the temporary name and syncs the root directory before reporting success. `DeleteUploaded` also syncs the directory after removal. Tests inject file-sync, object-directory-sync, and parent-directory-sync failures. A file-sync failure does not publish an object; a directory-sync failure returns an error and can leave a private orphan. A close and reopen of the store reads back the same bytes in the local test fixture. These operations provide the implemented local-filesystem durability boundary; power-loss guarantees still depend on the operating system and filesystem honoring file and directory sync.

When enabled, the total budget counts logical bytes of every private regular file found in the root, including promoted orphans and leftover upload temporaries; it does not use PostgreSQL rows as a proxy for disk use. A put performs a rooted scan and serializes quota-checked writes within that Store instance, so concurrent puts through the same instance cannot overbook the configured logical-byte limit; a caller waiting for the quota slot can cancel through its context. The quota gate is process-local: async deployment must use exactly one Go API process and one writer instance for each image root. Multiple API processes or multiple Store instances sharing a root are unsupported because their quota scans are not coordinated. The root must stay private, with Python mounted read-only and no concurrent external filesystem writers. Unsafe entries such as symlinks or directories make the quota scan fail closed with a generic storage error. Deletion frees capacity for a later scan. No automatic cleanup runs.

The package has no retention policy, database transaction, or automatic garbage collector. If a failure occurs after an object has been promoted, `Put` can return an error while the object remains. Callers must not infer transaction outcome from a storage error. Likewise, do not call `DeleteUploaded` after an ambiguous PostgreSQL commit: the row may have committed even if the client did not receive confirmation. If guarded deletion after a confirmed idempotency race fails, keep the orphan; it remains charged against the volume budget. Safe orphan discovery and cleanup require a later reconciler with database-aware policy.

## Stage 2 verification boundary

The package tests cover private root/file modes, root and object symlink rejection, UUIDv4 key shape, declared MIME normalization, size and empty-input bounds, no-overwrite collision behavior, traversal rejection, cleanup after an injected write failure, injected file/directory/parent sync failures, same-store/inode/content-checked deletion, and reading identical bytes after close/reopen. The optional total-budget tests cover negative configuration, persisted objects, leftover orphan/temp files, unsafe directory/symlink entries, freeing capacity after a confirmed deletion, reopen accounting, and concurrent puts through one Store. Intake-service tests cover digest binding to MIME and bytes, replay/conflict preflight without image writes, confirmed-race cleanup, unknown-commit retention, cancellation, and failed image writes. Stage 3 checks are package-level only; API composition and database integration remain later gates.

For the original stage 2 baseline on Go 1.25, `GOTOOLCHAIN=go1.25.0 go test ./internal/imagestore -count=1`, `GOTOOLCHAIN=go1.25.0 go test -race ./internal/imagestore -count=1`, and `GOTOOLCHAIN=go1.25.0 go vet ./internal/imagestore` passed. The Linux/arm64 test binary compiled and the original 14 top-level package tests ran successfully in a one-shot Linux container as UID `65532`; that container run did not exercise PostgreSQL or the Compose integration harness. Stage 3 quota and intake changes require their own current verification results before acceptance. These package-level results do not prove that the current API uses the store, that a job and outbox are committed with an image, or that a worker has read-only access to a shared mount. Those checks belong to later stages once intake and consumer wiring exist.
