# Архитектура

## Контекст

В продукте два репозитория: `passport-android` и `passport-backend`. В backend-репозитории находятся Go API и отдельный внутренний Python OCR runtime. Это два процесса с разными ролями; контейнерная упаковка возможна после проверки совместимости целевого компьютера, но не обязательна для локального запуска. Серверная композиция ограничивает bind заданным числовым локальным IP и проверяет адрес прямого TCP-клиента по непустому CIDR-списку, заданному вызывающим кодом. Это конфигурация LAN-доступа; она не настраивает маршрутизацию, firewall или Internet forwarding.

## Компоненты

### Go public API

Go владеет внешним HTTP контрактом. Публичные DTO/mapper находятся в `internal/api`, HTTP handler — в `internal/httpapi`, server composition — в `internal/server`, а `cmd/api` создаёт запускаемый процесс из явной JSON-конфигурации. Handler проверяет маршрут, request ID, multipart-форму, заявленный MIME type и размер, ограничивает конкурентные upload+recognition запросы и вызывает внутренний `Recognizer`. Production provider реализован в `internal/ocr`: он декодирует изображение, создаёт приватный job workspace, запускает внутренний Python worker и передаёт только проверенную каноническую extraction публичному mapper. Синхронный endpoint использует CIDR ACL, но не identity-auth; async jobs используют отдельные bearer credentials из optional конфигурации. Лимиты и LAN CIDR задаются оператором; универсальные production defaults не выбраны.

Operational logging принадлежит Go. `internal/telemetry` пишет JSON Lines в настроенный приватный файл, сериализует rotation и исключает параллельный второй writer для того же пути. HTTP handler сохраняет request UUID (включая допустимый регистр hex) в context; этот ID передаётся OCR job и worker telemetry. Логи содержат только фиксированный набор событий и категорий: безопасный маршрут/метод, HTTP status, длительности, код ошибки, OCR job outcome и ограниченные stage-поля. Файлы и их каталог приватные. Изображение, распознанный текст, source hash, имя файла, адрес клиента, URL query, непроверенные заголовки и причина исключения в service log не записываются.

Отдельный `internal/metrics.Store` хранит накопительные агрегаты в приватном JSON state-файле и атомарно сохраняет каждое завершённое HTTP/OCR/stage наблюдение. `GET /v1/stats` отдаёт snapshot через ту же прямую TCP peer CIDR ACL. Он содержит фиксированные status/error/stage категории и гистограммы длительности; request IDs, пользовательские метки, текст, изображения и per-request записи не хранятся. Это долговременные cumulative counters, не история по интервалам: темпы нельзя получить из одного snapshot. Перезапись state атомарна, но сбой между завершением события и сохранением может потерять последнее наблюдение; exactly-once гарантия отсутствует.

Локальная активация и same-host проверка 2026-10-30 подтвердили healthy state после перезапуска: один synthetic HTTP 422 и одна OCR failure отражены в counters, stats polls не включены в HTTP total. `since` относится к новому state file и не включает историю предыдущего процесса. Это подтверждает маршрут и персистентность агрегатов на проверенном хосте, но не Android-доступ с другого устройства и не availability/SLO.

Ограниченный macOS CPU HTTP integration case подтвердил 11 записей для одного запроса: 8 process-stage, 2 OCR job и 1 HTTP completion с общим request ID. Это подтверждает выбранный успешный путь и корреляцию в одном запуске, но не долговременную работу или deployment сервиса; детали и границы acceptance приведены в [runtime runbook](OCR_API_RUNTIME.md).

Отдельный локальный launch текущего `cmd/api` также проверен через same-host probes на настроенном LAN interface: `service.started`, HTTP 405/422, связанная с 422 terminal OCR job failure и пустой job workspace после ответов. Проверка относится к этому запуску; Android/remote-device access и долговременная эксплуатация не подтверждены.

### Текущий Python OCR runtime

Для текущего синхронного API Python OCR runtime запускается как приватный дочерний процесс Go и не имеет ingress/публичного порта. Единственный production provider — RussianDocsOCR: Go запускает один worker при старте, worker возвращает структурированные поля, а Go канонизирует даты, пол и код подразделения до публичного mapper-а. Старые API runtime на PaddleOCR-VL и Go layout/ROI/extraction pipeline удалены; связанные сравнения остаются историческими исследовательскими материалами. Детали конфигурации и протокола приведены в [runtime runbook](OCR_API_RUNTIME.md).

Worker использует stdout только для отдельного JSONL telemetry protocol с шестью allowlisted keys; subprocess stdout/stderr направлены в `DEVNULL`. Go parser проверяет schema, request ID, enum-значения, порядок фаз, границы размера и отсутствие лишних/дублирующихся ключей. Повреждённая telemetry отключается с максимум одним безопасным warning и не меняет результат OCR. `stage_completed` означает успешный exit соответствующей команды; только `ocr.job.completed` означает, что весь pipeline, проверка artifacts, extraction binding и workspace cleanup завершились успешно.

В async path Python consumer работает отдельным внутренним процессом с resident моделью. Go relay публикует committed outbox events, а Python получает минимальный RabbitMQ envelope, забирает image только для чтения и отправляет fields/error через приватный worker API. Go владеет PostgreSQL lifecycle и повторно использует `api.MapExtraction` для публичного canonical response. Эта связка требует `queue_processing` в Go config и запущенного consumer; при одном `async_jobs` job только сохраняется и остаётся `queued`. Код и controlled delivery/recovery acceptance stage 4 завершены. Приёмка подтвердила duplicate delivery и ACK-loss recovery без повторного OCR или изменения канонического результата; она не проверяла OCR качество на private production weights, TLS/ingress, HA или production rollout. Stage 5 owner-scoped status read прошёл bounded real PostgreSQL/API acceptance: PostgreSQL отдаёт Go минимальную проекцию одним read-only запросом с фильтром по job и владельцу; Go валидирует и сериализует сохранённый canonical result без второго mapper-а. Stage 6 Android flow принят через connected synthetic HTTP fixture и APK launcher test; live Android-to-Go-to-Python OCR остаётся отдельной проверкой.

Внутренний listener `/internal/worker/v1/*` использует отдельный worker bearer registry и отдельный private address; он не является публичной клиентской API. Consumer не имеет PostgreSQL credentials. Checked-in Compose включает внутренний `queue` profile для controlled stage 4 integration с shared image root. OCR source/model snapshot выбирает оператор и задаёт в конфигурации ожидаемые версии; исходники и weights не копируются в образ и не обновляются автоматически. API/image state остаются в отдельных persistent roots с сохранением operator UID/GID. Этот профиль не является production deployment acceptance и не подтверждает качество OCR на реальных private weights или HA.

Внутренний handoff между OCR pipeline и Go field assembler фиксируется схемами observations v1–v3: сырые строки, score и geometry привязаны к pass и transform в EXIF-нормализованных пикселях. Manifest, планы, crops, VL evidence и extraction остаются private job artifacts. Они валидируются и удаляются после обработки и не попадают в OpenAPI/public response. Добавление statistics endpoint не меняет DTO и response schema распознавания. Локальные A/B runners раздельно оценивают observations и field assembly; development-изображения не заменяют held-out выборку.

### Экспериментальные offline OCR-ветки

API сохраняет Go-owned валидацию канонических полей, статическую фильтрацию ошибок, lifecycle job workspace, request correlation, operational logs и cumulative stats. Worker не передаёт внутренние доказательства в HTTP response; публичный mapper по-прежнему требует ручную проверку результата.

After-v2 ограниченное comparison на пяти development-изображениях завершено; результаты и ограничения приведены в [документе автоматических VL ROI](OCR_AUTO_VL.md). Результат не является held-out оценкой и не меняет public API. Прежнее Go-only native-block comparison и отдельный ручной ROI контроль описаны соответственно в [Go results](OCR_VL_GO_RESULTS.md) и [manual ROI control](OCR_VL_ROI_CONTROL.md). Это не идентификация варианта документа, универсальное layout распознавание или подтверждение подлинности.

Цель — запуск на большинстве обычных настольных компьютеров и ноутбуков. Планируемая матрица проверки включает Windows, Linux и macOS на x86_64 и arm64, но не является гарантией универсальной поддержки всех устройств. Go API и Python OCR runtime выполняются на одном компьютере. CPU — обязательный базовый режим; GPU необязателен и применим только при подтверждённой поддержке выбранными runtime и оборудованием, без предположения о CUDA, Metal или ANE. Минимальные версии ОС, CPU и объём RAM будут определены по результатам пилота. Mac с Apple Silicon M1 и PC — только примеры машин для проверки. Используются только готовые предварительно обученные модели: обучение и fine-tuning не входят в объём. Основная пара весов и runtime для пилота предложены в [выборе модели](MODEL_SELECTION.md), но ещё не проверены.

## Поток запроса

1. В локальном сценарии Android передаёт снимок и необязательный `X-Request-ID` в `POST /v1/passport/recognize` на настроенные оператором локальные IP-адрес и порт. `cmd/api` читает explicit config; пример привязан только к loopback. Команда и full provider реализованы, но endpoint не публикуется сам по себе и не создаёт Internet ingress.
2. Handler требует один файл multipart field `file`, проверяет маршрут, request ID, метод, контекст и прямой TCP-адрес клиента до получения concurrency slot или чтения upload body. Пустой список разрешённых CIDR сохраняет прежнее unrestricted-поведение только для отдельно используемой handler library; `server.New` требует непустой список. Запрос с корректным маршрутом и метаданными, но адресом вне allowlist, получает `403 access_denied`. `X-Forwarded-For` и `X-Real-IP` не используются. Далее handler проверяет только заявленный `image/jpeg`, `image/png` или `image/webp`, multipart body и размер файла. Положительный `MaxUploadBytes`, `OCRTimeout`, `MaxConcurrent` и непустой `PipelineVersion` обязательно задаёт caller; production defaults не выбраны. Concurrency slot удерживается на время upload и распознавания. Нет отдельной rate/QPS policy.
3. Handler передаёт `Recognizer` байты file part и заявленный media type с дочерним context и configured timeout; сам handler image bytes не декодирует. Реальный provider проверяет фактический формат/декодируемость/размер пикселей, затем создаёт приватные 0700 workspace и 0600 input, запускает Python worker в принадлежащей ему POSIX process group, проверяет bounded private status/extraction и удаляет workspace при всех исходах. На macOS/Linux отмена посылает TERM, после grace — KILL группе, reaps direct child; `Close(ctx)` отменяет и дожидается активных jobs после HTTP server shutdown. Detached process groups не входят в гарантию.
4. `internal/api.MapExtraction` валидирует публичные значения и состояния, не выдаёт внутренние evidence, преобразует issues в статические безопасные сообщения и добавляет `no_fields_recognized`, если все публичные значения после фильтрации равны `null`. Отсутствие полей не становится `422`; этот статус передаётся только из `ErrImageUnprocessable` recognizer-а. Написанные handler-ом ответы 400/403/413/415/429/500/503/504 используют закреплённые error codes и correlation UUID в JSON/header.
5. Handler потоково читает multipart через ограниченный request body, удерживая bytes принятого файла для вызова `Recognizer`; сам handler временные файлы не создаёт. Provider хранит upload только в приватном временном workspace и удаляет его после обработки. API историю сканов не хранит.
6. Клиент использует только актуальный ответ для текущей операции/снимка/ревизии; исправления и подтверждение остаются в клиентском потоке до экспорта.

## Надёжность и безопасность

### Async jobs flow (этапы 3–7 приняты)

Синхронный `POST /v1/passport/recognize` сохраняет ответ `200`. Durable acceptance отдельного `POST /v1/passport/jobs` и owner-scoped `GET /v1/passport/jobs/{job_id}` прошли ограниченные integration gates этапов 3 и 5. Stage 4 outbox relay и Python consumer lifecycle также прошли controlled delivery/recovery acceptance. При настроенном `queue_processing` и запущенном consumer job может проходить `queued → processing → completed|failed`; если настроен только `async_jobs`, он остаётся `queued`. `202` подтверждает сохранение image/job/outbox, не завершение OCR. Предыдущая версия Android Compose flow прошла real PostgreSQL/API and connected synthetic HTTP fixture acceptance, включая запуск debug APK, но проверяла persistent job/result recovery; эти 67 JVM/16 connected tests исторические. Текущая RAM-only клиентская политика прошла 73 JVM tests, 19 instrumented tests, lint и debug/release builds. Это не live Android → Go → Python OCR и не OCR quality acceptance; финальная установка на физический телефон не выполнялась. OpenAPI и план приведены в [API_RESULT.md](API_RESULT.md) и [ASYNC_MIGRATION_PLAN.md](ASYNC_MIGRATION_PLAN.md); storage foundation — в [image store](IMAGE_STORAGE.md) и [PostgreSQL schema](POSTGRES_SCHEMA.md).

Go остаётся публичной границей и владельцем auth/ownership, idempotency, публичных DTO, canonical mapping, job status и результата в пределах выбранного retention. Для новой Android installation клиент генерирует индивидуальный `pbt1_` bearer secret и сохраняет его в encrypted private storage до регистрации. `POST /v1/client-installations` принимает только SHA-256 секрета; PostgreSQL хранит hash и созданный сервером `client_id`. Это anonymous installation identity, не пользовательский аккаунт и не проверка личности. Опциональный static hash registry остаётся для ранее provisioned клиентов. `internal/jobintake` связывает owner-scoped idempotency, private image storage и PostgreSQL repository. Изображение записывается первым, затем одной транзакцией фиксируются job и outbox; только подтверждённый commit даёт `202`. Неоднозначный commit outcome даёт безопасную ошибку и оставляет файл, чтобы committed job не ссылалась на удалённый object. Подтверждённые replay/conflict удаляют только новый проигравший upload; cleanup failure оставляет orphan, который продолжает занимать file quota. Outbox relay позднее публикует только `job_id` без изображения или паспортных данных.

Python — отдельный внутренний OCR consumer с resident моделью. На первом этапе один consumer обрабатывает одну задачу одновременно; duplicate delivery допускается, а claim/attempt token и проверка текущего состояния защищают от повторной записи результата. Worker передаёт структурированную extraction по приватному Go-owned completion boundary; Go применяет прежний `MapExtraction`, записывает canonical result и terminal state, затем worker подтверждает сообщение брокеру. ACK до durable completion недопустим. Состояния — `queued → processing → completed|failed`; ограниченные retry возвращают job в доступную очередь, а исчерпание retry переводит в terminal `failed`. Retry может изменить порядок выполнения; глобальный строгий порядок не является гарантией.

Каждый async job принадлежит principal из проверенного bearer credential. При enrollment Android отправляет SHA-256 хеш индивидуального секрета; backend связывает его с opaque `client_id`. JWT, login и пользовательского аккаунта нет. Enrollment ограничен прямым peer CIDR ACL и положительными операторскими caps; release credential traffic требует TLS. Raw secret не попадает на сервер, в logs, database или Git. Опциональный static registry обслуживает ранее настроенные credentials; enrollment hash, зарезервированный таким registry или отозванный в БД, отклоняется. Владелец никогда не берётся из body, CIDR или forwarding headers; async route отвечает `401` на отсутствующий/невалидный credential, а GET одинаково отвечает `404` для malformed, отсутствующего и чужого job. `Idempotency-Key` ограничен 1–128 видимыми ASCII символами и scoped к owner; digest связывает точные bytes и normalized media type; совпадающий повтор возвращает ту же job, иной digest даёт `409`. Одна DB транзакция не включает Rabbit I/O: stage 4 relay публикует durable outbox через confirms и mandatory routing, после подтверждения фиксирует публикацию и допускает безопасный повтор при неоднозначном сбое; обработка доставки идемпотентна.

`GET` отдаёт текущее состояние из Go/Postgres; `failed` также имеет HTTP `200` и безопасную категорию ошибки. В `completed` результат — существующий `RecognitionResponse`, без OCR text, кандидатов, evidence, файловых путей и runtime diagnostics. После receipt клиента или через фиксированные 15 минут от terminal time canonical result удаляется, после чего GET даёт `410 job_result_gone`; image cleanup начинается при terminal OCR. `POST /v1/passport/jobs/{job_id}/receipt` возвращает `204` для повторного безопасного ACK и `409` для nonterminal job. RAM-only Android capture/upload/job/result behavior прошёл 73 JVM tests, 19 instrumented tests, lint и debug/release builds: operational photo/document data, job state and result живут в RAM; receipt отправляется после применения результата к UI; process death не восстанавливает job и не повторяет upload. Явный 7z формируется в RAM и передаётся через private ContentProvider stream; export verification прошла, получатель может отдельно сохранить копию. Эти тесты не означают, что финальный APK установлен на физический телефон. Backend receipt/15-minute retention contract не меняется. Минимальные job/idempotency/attempt/outbox tombstones остаются как техническое состояние, но изображения и распознанный результат не архивируются. Idempotency key генерируется случайно как технический идентификатор; клиент не должен помещать туда персональный или документный текст. Зашифрованный технический backup может содержать этот caller-supplied key и другие metadata, поэтому сам архив остаётся чувствительным. В target API нет отмены, листинга или общей истории сканов. Stage 7 lifecycle/retention, revocation, readiness, snapshot и technical-backup component checks прошли bounded PostgreSQL/filesystem/Compose acceptance. TLS configuration и trusted test-certificate rehearsal прошли, но production domain/certificate не активированы. Durable config promotion и LAN cutover на `192.168.1.91:8080` за private Caddy прошли start/status/stop; прежний `18080` listener остановлен. Stage 8 bounded real-OCR/100-request workload run завершён, но quality/fault acceptance остаётся открытым; см. [report](STAGE8_ACCEPTANCE.md).

Handler stateless и принимает обязательную caller-конфигурацию upload bound, OCR timeout и concurrency; server composition также требует непустой allowlist клиентских CIDR и положительные read/header/write/idle/shutdown timeouts и `MaxHeaderBytes`. Каждый CIDR должен целиком находиться внутри loopback, RFC1918, IPv6 ULA или link-local диапазона; префиксы нормализуются и копируются. Bind принимает только конкретный числовой loopback/private/link-local IP с числовым портом, не wildcard, hostname или public IP. `Serve` проверяет фактический адрес переданного TCP listener и закрывает неподходящий listener до вызова `Accept`. ACL использует `RemoteAddr` прямого TCP peer и не доверяет proxy-forwarded headers. Настройка не подтверждает поведение внешней маршрутизации и не создаёт deployment/Internet proxy. Для ответа требуется `WriteTimeout > ReadTimeout + OCRTimeout`; проверка переполнения суммы безопасна, а реализованный предел `MaxHeaderBytes` предотвращает переполнение внутреннего `net/http` read limit и не является production numeric policy. Внутренняя composition однократна: `Run(ctx)` сама открывает настроенный TCP listener, а `Serve(ctx, listener)` принимает и закрывает переданный listener. При отмене она завершает accept, выполняет bounded graceful shutdown и при timeout принудительно закрывает соединения; goroutine `http.Server.Serve` дожидается завершения. Вложенный recognizer должен уважать request context, иначе его работу нельзя гарантированно остановить.

Handler не пишет upload во временные файлы до входа в intake service и не отражает filename, raw request ID или recognizer diagnostics в ответах. `http.Server.ErrorLog` направлен в discard; provider не захватывает stdout/stderr дочерних процессов и использует фиксированные error categories. Worker и pipeline sidecars доступны только внутри job workspace, проверяются и удаляются при завершении.
