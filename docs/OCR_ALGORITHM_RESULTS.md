# Результаты алгоритмического OCR-прототипа

**Статус: ограниченное сравнение прототипа завершено и проверено двумя независимыми читателями.** На этих двух примерах вариант C дал больше точных предложений по обязательным полям; это основание продолжать C как экспериментальный кандидат, а не объявлять глобального победителя или production-качество. Технические проверки ниже не являются доказательством качества распознавания.

## Объём и метод

Сравнение выполнено на двух локальных development-изображениях, обозначенных `sample-01` и `sample-02`. Это набор для разработки, а не независимая held-out-выборка. Для каждого документа оцениваются 10 обязательных полей; необязательное отчество учитывается отдельно и не входит в знаменатель `20` для двух документов. Сравниваются фиксированные варианты алгоритма на одинаковых OCR-наблюдениях и с одним и тем же эталоном. Сырые OCR-строки и значения полей в этот документ не включены.

Для оценки точного совпадения исправлена проверка enum gender: сравнивается форматируемое значение `M`/`F` с напечатанным словом. Это исправление scorer, а не улучшение OCR или извлечения; итоговые числа ниже рассчитаны после исправления. Других fuzzy-сопоставлений или карты исправления визуально похожих символов для подсчёта нет.

## Реализованные изменения прототипа

- Python preprocessing расширяет поиск строки консервативной рамкой вокруг bbox; добавляет crop-overlap для швов и два правых margin-прохода; MRZ-подобные области пропускаются, чтобы не смешивать их с полями основной страницы.
- Передаётся геометрия и происхождение кандидата для последующей оценки в Go; runtime фиксирует CPU provider.
- Go field assembler использует известные метки и пространственное расположение с ограниченными layout fallback-правилами; для дат и соседних полей сохраняются основания сопоставления.
- Нормализация имён остаётся только отдельным предложением; исходное OCR-значение сохраняется. Форматтер gender сопоставляет внутренний enum с печатной формой.
- Метки заголовка и издателя проверяются отдельно; область gender ограничена соответствующей зоной. Поиск по margin ROI допускается только для поля серии.
- При конфликте или неоднозначности assembler воздерживается от выбора и не использует эталон для выбора кандидата.

Эти правила не являются частью публичного API и не подтверждают безопасность автозаполнения. Не добавлялись новые веса, обучение/fine-tuning, API, Android-, Docker- или production-реализация.

## Исполнение и проверки

Новый OCR pipeline был выполнен на CPU. Для итогового сравнения OCR-наблюдения переиспользованы (`observations_reused=true`), поэтому значения OCR-времени относятся к предшествующему свежему запуску и не являются замером этого повторного сравнения. Исторический OCR-запуск включал пять проходов: три для `sample-01` и два для `sample-02`. Последующий быстрый прогон измерял Go post-processing; его время нельзя интерпретировать как end-to-end latency.

Проверки, подтверждённые главным агентом: 52 Go test cases завершились успешно. Набор Python теперь содержит 23 unit tests (16 region, 3 TSV, 4 runner); прежние 22 прошли, затем focused runner suite из 4 тестов также прошёл. Scorer после исправления формата gender был повторно проверен на сохранённых observations. Дополнительный быстрый foreground trial завершился с кодом 0 за 6,3 секунды. Эти проверки подтверждают только техническое выполнение указанных компонентов.

## Качество и ограничения

Счётчик ниже разделяет точные предложения, неверные предложения и отсутствующие/отвергнутые значения только для 10 обязательных полей. Счёт верных предложений не означает автоматически принятые поля: все предложения вариантов A/B/C остались `uncertain` и требуют ручной проверки.

| Вариант | `sample-01`: верно / неверно / пропуск | `sample-02`: верно / неверно / пропуск | Итого по обязательным полям |
|---|---:|---:|---:|
| A — исходные записи | 7 / 2 / 1 | 6 / 2 / 2 | 13 / 4 / 3 из 20 |
| B — записи плюс предложение нормализации имени | 8 / 1 / 1 | 6 / 2 / 2 | 14 / 3 / 3 из 20 |
| C — все подготовленные проходы плюс предложение имени | 9 / 1 / 0 | 6 / 2 / 2 | 15 / 3 / 2 из 20 |

Для необязательного отчества: в `sample-01` предложение неверно во всех вариантах. В `sample-02` A и B совпали с эталоном, а C оставил значение отсутствующим из-за двух конфликтующих кандидатов; renderer показывает `null` как `missing`, а не как `uncertain-wrong`. Поэтому B и C имеют по 15 точных предложений по всем полям в сумме, но C сохраняет дополнительное отсутствие необязательного значения. Нельзя сворачивать обязательные реквизиты и отчество в одну метрику без этой оговорки.

По варианту C оставшаяся ошибка обязательного поля в `sample-01` — место рождения; в `sample-02` неверны имя и орган выдачи, а пол и место рождения отсутствуют. Отчество в `sample-01` предложено неверно, в `sample-02` C воздержался. Ни одно значение не было автоматически принято как `recognized`; это означает ручную проверку для всех полей, а не отсутствие OCR-совпадений.

Переоценка сохранённых OCR-записей показывает изменение варианта C после добавления Go field association и serial-only margin ROI: на `sample-01` число точных предложений по обязательным полям изменилось с 6/10 до 9/10, на `sample-02` осталось 6/10. Сравнение использует те же исходные OCR-записи, изображения и хеши моделей, но сохранённые результаты были пересчитаны с текущим эталоном; независимый byte hash прежней версии эталона отсутствует. Исправление gender enum — отдельная коррекция метрики и не является OCR-приростом.

Из этого ограниченного протокола вариант C — предпочтительный кандидат для дальнейшей проверки обязательных полей. B и C делят число точных предложений по всем полям, а у C отчество в `sample-02` отсутствует из-за abstain. Два development-изображения не устанавливают глобального победителя, production accuracy или валидированную точность автозаполнения; 15/20 нельзя представлять как 75% production accuracy.

Предыдущие `6/11` для буквальных OCR-совпадений, описанные в [результатах раннего OCR-пилота](OCR_PILOT_RESULTS.md), относятся к прежней ограниченной проверке строк и не являются field-level метрикой; это не сопоставимый показатель до/после и не точность модели.

Для дальнейшей оценки нужны разрешённая выборка документов с разбиением по документам, held-out проверка, анализ ложных заполнений и пропусков, а также отдельные замеры end-to-end времени и ресурсов. Текущий быстрый замер Go post-processing не является end-to-end: на этом CPU-хосте OCR-проход занимает ориентировочно 2–3 секунды на документ, но это наблюдение на двух примерах, не широкий benchmark. Публичный API, интеграция с Android, производственная упаковка и широкая матрица ОС/архитектур не реализованы и не проверялись.
