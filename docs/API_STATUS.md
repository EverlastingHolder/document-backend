# Асинхронный статус задания

`GET /v1/passport/jobs/{job_id}` возвращает состояние одного задания, принадлежащего авторизованному владельцу. Этот read path не запускает OCR и не изменяет job. Он доступен только через индивидуальный bearer credential; `owner_id` берётся из проверенного principal. SQL-запрос фильтрует одновременно `job_id` и `owner_id`. Некорректный UUID, неизвестный ID и ID другого владельца дают одинаковый `404 not_found`. Ответы статуса и результата имеют `Cache-Control: no-store`.

Успешное чтение возвращает HTTP `200` для всех сохранённых состояний:

- `queued`: `finished_at` равен `null`; `started_at` равен `null` до первой попытки и может сохранять время предыдущей попытки после retry.
- `processing`: `started_at` задан, `finished_at` равен `null`.
- `completed`: обе временные метки заданы; `result` содержит существующий canonical `RecognitionResponse`.
- `failed`: `finished_at` задан, `started_at` может быть `null`, если задание завершилось до начала OCR; `error` содержит только стабильный безопасный код и статическое сообщение.

Завершённый ответ читается из `jobs.result` и не пересчитывается через `MapExtraction`, OCR pipeline или текущую конфигурацию. Перед выдачей сервис проверяет структуру сохранённого ответа: идентификатор результата совпадает с `job_id`, `pipeline_version` совпадает с версией, записанной рядом с результатом, а envelope и все 11 публичных полей имеют допустимые ключи, типы, состояния и безопасные issue codes. Проверка возвращает исходный JSON snapshot; она не исправляет и не нормализует значения. Повреждённый или несогласованный snapshot даёт общий `503 job_status_unavailable`; его содержимое и причина ошибки не включаются в ответ.

Для `failed` HTTP остаётся `200`: клиент читает конечное состояние из тела ответа. Публичное сообщение выбирается из фиксированной таблицы для `image_unprocessable`, `processing_failed`, `ocr_unavailable` и `processing_timeout`. Ошибки базы, traceback, пути, токены, исходные OCR-данные и персональные данные не входят в это сообщение.

`X-Request-ID` относится к отдельному HTTP GET и служит корреляцией запроса. `result.request_id` остаётся UUID задания и не заменяется ID GET-запроса. По выбранной политике canonical result удаляется при явном receipt ACK клиента либо через 15 минут после terminal state. Job/idempotency tombstone остаётся как техническая запись, чтобы повтор того же owner/key не создал новый job и не восстановил удалённый payload. После durable purge marker status GET возвращает `410 job_result_gone`, даже если периодическая уборка ещё не выполнилась. Изображение удаляется после terminal OCR decision; неудачная файловая уборка повторяется и может временно оставить файл на volume. Это не обещание физического secure wipe при сбое носителя. Ресурс не предоставляет список, историю или отмену заданий.

Stage 5 реализован и принят: публичный GET с owner-scoped PostgreSQL read path прошёл ограниченную реальную PostgreSQL/API-проверку для новых и повторно поставленных в очередь, выполняющихся, успешных и неуспешных заданий, включая проверки доступа и corrupt snapshot. Это подтверждает контракт и интеграцию на проверенном Compose-профиле, но не качество распознавания на выбранных private weights и не production rollout. Android polling принято на этапе 6 через connected synthetic HTTP fixture.

`POST /v1/client-installations` — hash-only enrollment новых клиентских установок. Он принимает только `token_sha256` (64 lowercase hex), не требует bearer auth, возвращает `201` при создании или `200` при replay и одинаковый `client_id`/`created_at` для того же hash. Секрет генерируется и сохраняется клиентом до регистрации; backend хранит только hash и случайный installation ID. Это не login и не пользовательский аккаунт. Enrollment включается через optional `async_jobs.client_enrollment` с положительными operator caps, проходит CIDR ACL и недоступен, если конфигурация отсутствует. Legacy static registry остаётся поддержанным. Stage 6 backend enrollment/auth прошёл real PostgreSQL/API acceptance. Ранее Android версия прошла 67 JVM tests и 16 connected tests с persistent job/result recovery; это историческое evidence прежней схемы. Текущая RAM-only capture/upload/job/result коррекция проверена 73 JVM tests, 19 instrumented tests, lint и debug/release builds. CameraX передаёт full-resolution image in memory без capture-файла; picker/upload/preview/job/result state не сохраняются для восстановления после process death; receipt отправляется после применения terminal result к live UI memory. Явный 7z формируется в RAM и передаётся через private ContentProvider stream; export verification прошла, получатель может сохранить отдельную копию. В connection profile сохраняются server URL и скрытый installation credential; credential защищён Android Keystore. Это технические настройки, а не сохранённые документы, jobs или результаты. Эти проверки не являются live Android-to-Go-to-Python OCR или production rollout; финальный APK на телефон не устанавливался по решению пользователя. См. [OpenAPI](../api/openapi.yaml), [план миграции](ASYNC_MIGRATION_PLAN.md) и [проверки API](TESTING.md).


`POST /v1/passport/jobs/{job_id}/receipt` — owner-scoped acknowledgment после применения terminal result к живому UI state в памяти клиента. RAM-only capture/upload/job/result flow проверен Android tests/builds: оперативные image/document bytes, job state и result не сохраняются для восстановления после process death; автоматических resume/re-upload нет. Явный 7z формируется в RAM и передаётся через private ContentProvider stream; получатель может отдельно сохранить копию. Пустой POST возвращает `204` при первом или повторном receipt, `409 job_not_terminal` для queued/processing и общий `404 not_found` для malformed/missing/foreign IDs. Receipt немедленно удаляет server-side result; повторный idempotency POST сохраняет исходный job ID, но не возвращает payload. Result также удаляется спустя фиксированные 15 минут от terminal time. GET после удаления возвращает `410 job_result_gone`. Изображения удаляются после terminal OCR decision; cleanup повторяется, если filesystem недоступна.

`GET /healthz` и `GET /readyz` — private deployment probes, не клиентские endpoints: liveness возвращает пустой `204`, readiness проверяет PostgreSQL и открытый image root с bounded context, но не RabbitMQ. Health paths не должны публиковаться через Caddy. `cmd/client-admin revoke` отзывает database-enrolled installation без удаления hash tombstone; `revoke-hash` сохраняет такой tombstone для static-only hash, который нужно запретить к повторной enrollment. UUID-команда сама по себе не отзывает static-only credential: его также удаляют из registry и перезапускают API. При настроенном DB lookup revoked hash перекрывает совпадающую stale static запись. Enrollment active cap считает только активные установки. `cmd/passport-ops snapshot` выдаёт только агрегированные queue/lease/cleanup/image-quota показатели и флаги операторских thresholds, без ID, hashes, OCR или PII; это операторский snapshot, а не доставка alert notifications. Технический backup исключает изображения/result payloads, raw bearer значения и file paths, но может включать caller-supplied `Idempotency-Key`; поэтому ключи должны быть случайными opaque IDs без персонального/документного текста, а encrypted archive следует считать чувствительным.
