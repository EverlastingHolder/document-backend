# PostgreSQL storage foundation

## Scope and status

This document covers the PostgreSQL foundation, durable intake, stage 4 job lifecycle, stage 5 status projection, stage 6 installation enrollment, and stage 7 result/image retention storage. The connection, forward-only migration runner, read-only schema readiness check, embedded schema, atomic job-plus-outbox intake, outbox publish leases, attempt claims, fenced completion/retry transitions, single-query owner-scoped status projection, and hash-only installation registry are implemented. Stages 3–5 passed bounded integration gates. Stage 6 backend enrollment/auth passed real PostgreSQL/API acceptance; the Android client flow passed connected synthetic-fixture and APK-launch acceptance. Stage 7 retention/receipt/revocation code is under implementation and remains subject to final integration/deployment acceptance. Live Android-to-Go-to-Python OCR and production rollout are not established.

The current synchronous `POST /v1/passport/recognize`, OCR worker lifecycle, and metrics JSON state file remain separate. `internal/metrics` aggregates are not a job database. The intended transition and stage gates are in [ASYNC_MIGRATION_PLAN.md](ASYNC_MIGRATION_PLAN.md).

## Embedded schema

Forward-only SQL migrations are embedded under `internal/jobstore/postgres/migrations/` and recorded in `schema_migrations` with a SHA-256 checksum. The runner applies pending migrations in version order inside one PostgreSQL transaction while holding a transaction-scoped advisory lock. It rejects duplicate/invalid embedded versions, unknown previously-applied versions, and changed name/checksum for an applied version. There is no automatic down-migration command; schema rollback or repair is an operator-led action.

The schema supports the async contract:

- `jobs` uses an opaque UUID `job_id`, opaque `owner_id`, owner-scoped visible-ASCII idempotency key and SHA-256 request digest. Clients must generate the key as a random opaque technical identifier and must not include personal, passport, or document text; the API syntax remains 1–128 visible ASCII characters. The table also stores an opaque UUIDv4 `image_key` plus media type/size metadata, an optional pipeline version, one of `queued`, `processing`, `completed`, `failed`, state timestamps, and optional canonical `result` or safe terminal error code. The worker supplies the actual pipeline version when it reports a result; no acceptance-time version pin is selected.
- A unique `(owner_id, idempotency_key)` constraint makes duplicate keys for one owner impossible at the storage layer. The caller-supplied key is retained technical metadata and must be treated as sensitive; a technical backup can contain it. A 32-byte digest is stored for comparing retries; do not put it in logs or aggregate telemetry.
- `jobs` constraints keep result/error fields consistent with state and timestamps ordered. A requeued job may retain its last `started_at`; `processing` requires a start and no finish, `completed` requires a JSON-object result and start/finish, and `failed` requires a terminal error code and finish. SQL checks the JSON object shape only; Go remains responsible for producing the exact existing `RecognitionResponse` through the canonical mapper and mapping a safe error message from the closed error code.
- `job_attempts` stores one row per `(job_id, attempt_no)` with a server-generated fencing token, lease expiry, lifecycle timestamps and a small state set. The initial event is attempt 1; the row is created only when a consumer successfully claims it. Late worker callbacks must match the current attempt token.
- `outbox` stores job ID, event type/schema version, attempt sequence and publish bookkeeping. Migration `0007_outbox_publish_lease.sql` adds paired claim token/expiry fields and an expiry index. The relay leases due rows in a short transaction, publishes outside that transaction, and marks them published only while its lease remains current. A confirm received before a crash but not committed to PostgreSQL can be published again; duplicate delivery is expected and must be idempotent. Error fields are constrained to code-like categories; never store exception text. The table has no image bytes, OCR text, owner ID, credentials or filesystem path.
- `client_installations` (migration `0008_client_installations.sql`) maps a unique 32-byte SHA-256 token hash to a server-generated opaque `client_id` and `created_at`; nullable `revoked_at` prevents a revoked hash from being enrolled again. The raw bearer secret is never stored. Registration serializes the active-client cap/rate check, looks up an existing hash before applying new-client limits, and returns its original ID and creation time on replay. Revoked rows remain non-reactivatable tombstones but do not consume the active-client cap. The table contains no device identifiers, owner-supplied data, or personal information.
- Migration `0009_data_retention.sql` makes image metadata nullable only after a terminal image cleanup claim succeeds, adds an image hash/purge marker/claim lease and a result-purge marker, and enforces the permitted terminal result states. It does not delete job/idempotency tombstones, attempts or outbox fencing rows; job metadata can include the client-supplied idempotency key and must not be described as universally non-PII. Completed canonical result JSON is nulled by receipt ACK or DB-clock expiry; the selected result window is fixed at 15 minutes after terminal time. Failed rows retain only a safe error category; receipt marks the payload lifecycle complete. Image files are guarded-deleted from the filesystem before PostgreSQL clears their object metadata, with leased retries after failures.

The source image remains in a separate private persistent file store, identified in PostgreSQL only by an opaque `image_key`. The filesystem write and PostgreSQL commit cannot be one atomic transaction: the acceptance flow writes the image first, commits job+outbox next, and may return `202` only after commit. The selected Stage 7 policy removes images after terminal OCR and removes canonical results at receipt ACK or after 15 minutes. The technical-backup allowlist excludes image bytes, canonical result payloads, raw bearer tokens, and image paths, but can include client-supplied idempotency keys and other opaque identifiers; treat the encrypted archive and its key as sensitive files and never use personal/document text as a key. Job/idempotency and attempt/outbox technical metadata remain indefinitely unless a future bounded tombstone-retention policy is separately selected.

## Intake and execution repository boundaries

`internal/jobs` owns job, envelope, claim, attempt, and execution repository types. `internal/jobstore/postgres` implements owner-scoped idempotency lookup and `CreateQueued`, plus leased outbox selection, publish acknowledgement/failure, consumer claim, fenced completion/failure, poison-event rejection, and expired-lease recovery. A successful create inserts a `queued` job and its initial `recognition.requested` outbox row (`schema_version=v1`, `attempt_no=1`) in one PostgreSQL transaction. `jobs.attempt_count` counts successful claims; each retry event uses the next number, and a `job_attempts` row is created only when a consumer claims that event.

Stage 4 transitions use PostgreSQL time for `available_at`, `started_at`, `finished_at`, and lease comparisons. A claim locks the matching job/event, checks the expected attempt sequence, and commits a processing attempt before the worker starts OCR. Completion stores the canonical Go response and marks job/attempt completed in one transaction. Failure either writes a new due time plus next outbox event, or writes terminal failure, in one transaction before RabbitMQ ACK. The retry count, initial delay, max delay, lease duration, hard processing timeout, completion budget, and outbox publish/reconnect timing are explicit operator configuration; the schema does not choose product defaults or retention.

The private worker API and JSON contract are described in [WORKER_PROTOCOL.md](WORKER_PROTOCOL.md). It is distinct from the public status GET. The Python consumer has no direct PostgreSQL access; Go owns state transitions and canonical response mapping.

The stage 5 repository method `GetOwnedStatus` performs one read-only query filtered by both `job_id` and authenticated `owner_id`. Unknown, malformed, and foreign job IDs map to the same not-found result. Its `jobs.StatusRecord` projection contains only the public job ID/state/timestamps, stored canonical result JSON, pipeline version, and safe terminal error code; it excludes owner binding, idempotency key/digest, and image metadata. It does not lock or mutate a job, and the primary-key lookup needs no migration or additional index. Go validates the stored state/result before returning the status response and reuses the stored canonical result without a second mapper. There is no list/history endpoint. Receipt ACK and fixed result expiry remove canonical payload; the row remains as a technical idempotency tombstone.

If `(owner_id, idempotency_key)` already exists, the repository returns the winning job as a replay only when the fixed 32-byte request digest matches. A differing digest is a conflict outcome. The lookup and conflict are scoped to the supplied authenticated owner. The repository returns only a generic unavailable error for database failures and never includes the DSN or driver diagnostic. Any create error, especially a commit error, may leave the transaction outcome unknown; callers must retain the newly written image and must not interpret the error as proof of rollback. Only a confirmed replay/conflict lets the upload layer consider guarded deletion of the just-uploaded, unreferenced image.

The API runtime calls `Store.CheckSchema` when asynchronous intake is enabled. This check is read-only: it requires all embedded migrations and the core job tables to be present and rejects migration drift. It does not run migrations at API startup. Apply schema changes, including migration 0008 before enabling client enrollment and migration 0009 before enabling retention lifecycle, using the explicit `cmd/migrate` command.

## Migration command and secret handling

`cmd/migrate` accepts a connection string through `DATABASE_URL` (or another named environment variable) or a mounted secret file. It does not accept the connection string as a command-line argument and emits only a generic failure line; driver diagnostics and DSNs are not printed. Supply positive timeouts explicitly:

```sh
go run ./cmd/migrate \
  -dsn-env DATABASE_URL \
  -connect-timeout 10s \
  -migration-lock-timeout 30s \
  -migration-timeout 2m
```

For a file-mounted secret, replace `-dsn-env DATABASE_URL` with `-dsn-file /run/secrets/postgres_dsn`. Do not store a live DSN in checked-in configuration or build arguments. The migration executable can be invoked as a one-shot Compose migration service before the API is ready to serve.

## Configuration and limitations

The driver is `github.com/jackc/pgx/v5` pinned at `v5.12.0`; the module Go directive is `1.25.0` as required by that dependency. `Open(ctx, Config{DSN, ConnectTimeout, MigrationLockTimeout})` opens a small bounded pool and performs a bounded ping. `Ping(ctx)`, `Migrate(ctx)`, `CheckSchema(ctx)`, owner-scoped `Lookup`/`CreateQueued`, enrollment `RegisterClientToken`/`LookupClientOwner`, and `Close()` are the exported storage APIs; no raw pool is exposed as an application API.

The connection errors and migration failures are returned as closed generic categories so callers cannot accidentally log credentials or raw database diagnostics. The encrypted technical-backup format contains allowlisted identity/idempotency tombstones only; it excludes image bytes, recognized fields/result payloads, raw bearer values, and image paths. Metadata still includes a caller-supplied idempotency key, so archive contents are sensitive despite encryption and the client contract prohibits personal/document text in the key. The implementation does not define a production database URL, technical tombstone cleanup threshold, job deadline, payload backup, or high availability. The planned deployment is single-host; persistent volumes do not protect against loss of the host.
