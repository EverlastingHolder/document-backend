# План работ

## Статусы

- **Готово:** документационная структура, требования, архитектура, закреплённая модель OpenAPI и Go prototype извлечения полей.
- **Реализован ограниченный Go API slice:** OpenAPI 3.0.3 contract 0.4.0, public DTO/mapper (`internal/api`), injected HTTP handler library (`internal/httpapi`) и внутренняя single-use server composition (`internal/server`) покрыты синтетическими Go tests. Composition требует явные runtime limits, конкретный числовой локальный bind IP, непустые caller-supplied client CIDRs и `Recognizer`, проверяет прямой TCP peer, владеет TCP listener и поддерживает bounded graceful shutdown с forced connection close при истечении независимого deadline. Запускаемая команда (`cmd/api`) и production recognizer wiring отсутствуют; подключение реального OCR явно отложено. Android integration, identity-auth/rate policy, production numeric limits и deployment остаются впереди.
- **Готово:** строгий Go parser национальной MRZ внутреннего паспорта РФ по приложению 24 к приказу МВД №773, с проверками контрольных цифр, codec modified-CLEER и сохранением частичной даты рождения без вывода века.
- **Готово:** внутренний handoff observations v2 и экспериментальная OCR-ветка MRZ, включая RapidOCR на CPU и необязательный Tesseract reader. Go extraction принимает `MRZPolicy=off|augment`; значение по умолчанию `off`.
- **Первый MRZ-срез завершён:** на двух development-изображениях `off` и `augment` дали одинаковые 15/20 точных предложений по обязательным полям (sample-01: 9/10, sample-02: 6/10); 3 предложения неверны, 2 поля отвергнуты/пропущены. Отчество sample-01 изменилось с неверного предложения на abstain. Один из двух образцов дал национальную пару с четырьмя валидными check digits; второй не дал валидной пары. Это не held-out оценка и не общая accuracy; подробности — в [результатах MRZ-среза](OCR_MRZ_RESULTS.md).
- **Срез разрешения detector завершён:** native 736/min и primary 1280/min дали соответственно 15/3/2 и 15/2/3 правильных/неверных/abstain предложений из 20. Новых правильных полей при 1280 нет; отчество осталось отсутствующим, все поля требуют ручной проверки. Default остаётся 736/min, а 1280/min — экспериментальным primary profile с auxiliary 736/min для margin/MRZ. Два кандидата изменившегося `given_name` на sample-02 не совпали с gold при post-hoc canonical comparison (0/2); gold не участвовал в выборе. Это не held-out оценка или общая accuracy; [подробный отчёт](OCR_RESOLUTION_RESULTS.md).
- **Граница результата:** `augment` добавляет диагностику и предложения по полям, а не подтверждённые значения. Поля требуют проверки человеком. Check digits удостоверяют только согласованность прочитанных символов в соответствующих элементах; они не устанавливают подлинность документа. MRZ не содержит места рождения и полного имени органа выдачи.
- **Не проверено:** обобщаемое качество OCR/MRZ и сборки полей на разрешённой held-out выборке, частота ложных заполнений и ручных исправлений, время и память на целевой матрице. Ограниченные числа по двум development-изображениям не являются общей точностью или production-результатом.
- **Экспериментальный offline pipeline реализован и сравнение after-v2 завершено:** source-image OCR с попыткой регистрации, Go-планированием автоматических ROI, PaddleOCR-VL чтением crop и повторной Go-проверкой private evidence. Coverage составил `19/30` областей (`6/3/6/1/3`). На 50 обязательных полях baseline дал `27/9/14` correct/wrong/abstain; `union` — `26/6/18`, `primary` — `30/8/12`. У `primary` единственная loss — correct→wrong `issuer` на sample-05; net изменение correct составляет +3. Все результаты требуют review. Ошибочные after-v1 sidecars исключены из scoring. Прошли 20 Python tests (11 reader, 5 generic-runner, 4 evaluation guards) и полный Go test suite. Метод, отдельные метрики и ограничения: [OCR_AUTO_VL.md](OCR_AUTO_VL.md).
- **Ограничения автоматического плана:** неполные или неоднозначные строки ФИО приводят к пропуску роли; planner не додумывает имена. Четыре вручную выбранных ROI из отдельного post-hoc контроля не являются automatic-ROI оценкой. Идентификация произвольного layout, широкая held-out валидация и production-качество не установлены.
- **Экспериментальные стадии не подключены к public API:** registration/template route, Go ROI planner и VL evidence работают только в локальном offline workflow. Перспективная коррекция, универсальная идентификация layout, production recognizer wiring и deployment остаются незавершёнными.
- **Не реализовано:** runnable внешний процесс/команда (`cmd/api`), production recognizer/OCR wiring, TLS, identity-auth, публикация, deployment и нагрузочная проверка. Handler library допускает пустой allowlist только для прежнего standalone-поведения; `server.New` требует caller-supplied LAN CIDR и конкретный локальный bind IP. Публичная response-модель и mapper работают отдельно от OCR.
- **Принятый объём:** только готовые предварительно обученные модели; обучение и fine-tuning не входят. CPU — базовый режим. GPU/иной ускоритель возможен только при подтверждённой поддержке runtime и оборудования; матрица ОС/архитектур и минимальные ресурсы ещё не проверены.

## Этапы

1. Согласовать с `passport-android` ошибки, идентификатор операции, отмену/повтор, состояния полей и обработку устаревшего ответа.
2. Закрыть продуктовые вопросы авторизации, передачи результата, минимальной Android-версии, лимитов и SLO.
3. Завершён MRZ-срез `off`/`augment` и ограниченное сравнение detector 736/min против экспериментального primary 1280/min; ни одно не дало новых правильных предложений сверх 15/20 на двух development-фотографиях. Сохранить 736/min default; не делать threshold fix по этим двум образцам.
4. Завершённый sanitized after-v2 aggregate показывает раздельно качество на пяти development-изображениях, coverage плана, incumbent baseline и ручной 4-ROI контроль. Следующий шаг — held-out проверка с разделением по документам; оценивать неверные предложения, abstain и ручные исправления. Не помещать реальные данные в обычные fixtures, Git или логи.
5. Геометрический probe ранее отклонил два development-снимка (`edge_support_insufficient`); позже были реализованы отдельные экспериментальные registration/template и automatic ROI маршруты. Эти результаты не подтверждают универсальную идентификацию layout или готовность autofill; перспективная коррекция и обобщаемое качество требуют отдельной проверки.
6. Зафиксировать внутренний OCR protocol/runtime и lifecycle только после отдельного решения о подключении; этот этап отложен пользователем. Не подменять его тестовым recognizer в production.
7. После отдельного решения о recognizer wiring — определить production limits и provider contract, затем добавить runnable Go command вокруг `internal/server`, определить/проверить LAN deployment и cleanup на целевых компьютерах; Android integration и решение о дополнительной identity-auth также остаются незакрытыми. Не подставлять временный или тестовый provider вместо отложенного OCR решения.

Этапы не означают, что проверка качества или production-развёртывание уже состоялись. Успешные тесты формата и check digits не заменяют оценку на документах. Полный аудит проекта не проводился.
