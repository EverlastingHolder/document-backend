# План перехода к асинхронному распознаванию

## Цель и границы

Этот план описывает поэтапный переход текущего Go API и приватного Python OCR runtime к асинхронной обработке. Целевой deployment разделяет Go API, Python OCR consumer, PostgreSQL и RabbitMQ; Go остаётся владельцем публичного API, канонического результата и состояния jobs. Python остаётся внутренним consumer без публичного порта и доступа к PostgreSQL. Исходный sync OCR path всё ещё запускает Python child process из Go. Первый целевой deployment — один хост; отказоустойчивость между хостами и HA не входят в scope.

Плановая дата фиксации: 2026-10-31. Этапы 1–7 завершены. На Stage 8 выполнен bounded real-OCR/100-request workload run, но общий quality/fault acceptance остаётся открытым; агрегаты приведены ниже. Stage 3 acceptance подтверждена реальной PostgreSQL + filesystem + HTTP composition. Stage 4 code и bounded delivery/recovery acceptance прошли контролируемый PostgreSQL/RabbitMQ/Go/Python harness. Queue delivery в deployment требует настроенного `queue_processing` и отдельно запущенного consumer; одних `async_jobs` достаточно для durable acceptance, но не для OCR processing. Stage 5 status endpoint принят. Stage 6 backend enrollment прошёл реальную PostgreSQL/API проверку, а Android app flow принят через synthetic HTTP fixture и запуск APK. Эта проверка не была live Android → Go → Python OCR и не оценивает качество на private production weights; финальная установка APK на телефон отложена пользователем. Production domain/certificate activation не выполнялась. TLS configuration и trusted test-certificate rehearsal прошли. Scope этапа 2 уточнён после проверки зависимости: его acceptance ограничена infrastructure/storage foundations; HTTP intake и consumer появились на этапах 3–4.

## Текущее состояние

- Backend пока состоит из двух репозиториев: `passport-backend` и соседнего `passport-android`.
- `POST /v1/passport/recognize` синхронно принимает один multipart image и возвращает завершённый ответ `200`. При занятом лимите конкурентной обработки запрос отклоняется `429` до чтения upload body.
- Go владеет HTTP контрактом и mapper-ом канонического `RecognitionResponse`. Python RussianDocsOCR запускается Go как один приватный процесс, получает JSON через stdin/stdout и работает с локальным путём изображения; модель остаётся resident в worker. Публичного Python порта нет.
- Текущая серверная конфигурация требует числовой локальный bind address и явный CIDR allowlist. CIDR проверяет сетевой peer, но не устанавливает личность владельца. Legacy sync route по-прежнему без user identity. Асинхронная установка автоматически создаёт индивидуальный bearer credential и регистрирует только его SHA-256 hash через `POST /v1/client-installations`; входа в аккаунт, пользовательской identity-проверки и общего APK token нет. Async jobs используют owner principal после enrollment либо поддерживаемый legacy static hash registry.
- Текущая телеметрия включает privacy-filtered operational logs и локальные персистентные cumulative metrics. Они не являются очередью jobs или журналом пользовательских операций.
- Stage 3 optional intake is connected to the hash-only client auth registry, PostgreSQL repository and private image store; its real PostgreSQL + filesystem + HTTP acceptance gate passed. Stage 4 code connects the outbox relay, private Go worker API, Python consumer, attempt fencing, DB-backed retries and expired-lease recovery; controlled end-to-end delivery/recovery acceptance passed. Stage 5 owner-scoped status read passed its real PostgreSQL/API acceptance gate. If `queue_processing` is absent, accepted jobs remain queued; if configured without a running consumer, OCR cannot finish. API startup checks schema read-only and does not auto-migrate. The status endpoint is available for polling. Stage 6 is accepted: installation enrollment/auth and Android Compose flow passed bounded real PostgreSQL/API, connected fixture, and APK launch gates. This does not establish live Android-to-Go-to-Python OCR, OCR quality on selected private weights, production deployment readiness, or capacity.

## Целевой контур

Целевой контур включает отдельные Compose services для Go API, Python OCR consumer, PostgreSQL и RabbitMQ. Checked-in Compose `queue` profile прошёл controlled stage 4 integration, но не production acceptance: deployment требует операторский config/secrets, сохранённый API state root, image root и выбранный read-only OCR source/model snapshot; model/source version expectations задаются оператором и не вызывают auto-upgrade, реальные веса не копируются в образ. Stage 3 сохраняет job и outbox транзакционно; stage 4 publisher и fenced lifecycle проверены вместе с consumer. Shared image store доступен Go на запись и Python только на чтение в tested integration profile. PostgreSQL — источник истины для job state, попыток, lease, результата и outbox. RabbitMQ содержит минимальный envelope (`schema_version`, `event_id`, `job_id`, `attempt_no`), но не изображение, OCR текст, персональные данные или файловый путь. Python не получает credentials к базе.

```mermaid
flowchart LR
    Client[Android client] -->|multipart POST /v1/passport/jobs| API[Go API]
    API -->|durable image| Files[(Private shared file volume)]
    API -->|transaction: job + outbox| PG[(PostgreSQL)]
    API -->|202 + job_id| Client
    PG -->|available outbox rows| API
    API -->|confirmed minimal envelope| MQ[(RabbitMQ)]
    MQ -->|manual-ack delivery, prefetch 1| Worker[Python OCR worker]
    Worker -->|read-only image| Files
    Worker -->|start / complete / retry schedule| API
    API -->|state, canonical result, outbox| PG
    Client -->|GET /v1/passport/jobs/{job_id}| API
```

### Публичный и внутренний контракт

- `POST /v1/passport/jobs` принимает тот же тип изображения через multipart. Он отвечает `202 Accepted` с opaque `job_id` и указателем для polling только после долговечной записи изображения и одной PostgreSQL транзакции с job и outbox event. Текущий `POST /v1/passport/recognize` сохраняет синхронную семантику `200` во время миграции; изменение `200` на `202` без отдельного маршрута запрещено.
- `Idempotency-Key` обязателен для нового POST и ограничен 1–128 видимыми ASCII символами. Клиент генерирует случайный opaque технический ключ и не включает персональный, паспортный или иной текст документа; ключ scoped к владельцу из проверенного auth principal, owner в body не задаётся. Повтор того же owner/key с тем же digest возвращает ту же job, включая terminal state, пока запись доступна. Тот же owner/key с другим digest возвращает `409`.
- `GET /v1/passport/jobs/{job_id}` доступен только владельцу. Успешное чтение известной владельцу job возвращает `200` для любого состояния: `queued`, `processing`, `completed`, `failed`. Некорректный UUID, отсутствующая job и job другого владельца возвращают одинаковый `404`. `GET` не блокирует и не меняет job; ответ строится по одному owner-scoped чтению и содержит `Cache-Control: no-store`. Для завершённой job поле `result` использует сохранённую каноническую Go-модель `RecognitionResponse` без повторного mapping; это результат распознавания и он по-прежнему требует проверки человеком. Для `failed` возвращается стабильная безопасная публичная ошибка без traceback, путей, raw OCR и персональных данных. Timeout/недоступность status storage возвращает статический `503 job_status_unavailable`. Ресурс не предоставляет список, историю, отмену, индивидуальную настройку срока хранения или обещанный интервал polling.
- Выбран HTTP Bearer transport с индивидуальным opaque token на каждой client installation. Android генерирует `pbt1_` + 32 случайных байта base64url и сначала сохраняет его в encrypted private storage, затем отправляет только SHA-256 hash в `POST /v1/client-installations`; raw token никогда не покидает клиент во время enrollment. Это anonymous installation enrollment, без login/user account и без заявления о проверенной личности. Backend возвращает стабильный случайный `client_id`; одна и та же хеш-сумма после потери HTTP-ответа возвращает прежние `client_id` и `created_at`. PostgreSQL хранит hash и client ID, но не raw secret. Новая установка/reinstall с новым ключом получает новый owner principal. Опциональный статический hash registry остаётся для совместимости ранее provisioned clients; worker credential остаётся отдельным `pwt1_` purpose. Входные caps `max_clients` и `max_new_clients_per_minute` положительны и задаются оператором; у них нет автоматических production defaults. Enrollment всё равно проходит прямой peer CIDR ACL. Release traffic с bearer credential требует TLS; локальный HTTP разрешается только явной debug-конфигурацией.
- Private worker listener использует отдельный purpose-specific `pwt1_` token и `passport-worker-credentials/v1` hash registry. Worker credential не является клиентским `pbt1_` credential; raw token выдаётся отдельному OCR consumer через защищённую provisioning procedure. Точные команды и registry boundary приведены в [WORKER_RUNTIME.md](WORKER_RUNTIME.md).
- Внутренний consumer использует durable delivery, manual ACK и prefetch `1`. Он подтверждает исходную доставку только после того, как Go зафиксировал `completed`/`failed` либо транзакционно сохранил отложенный retry. Временные retry планируются authoritative в PostgreSQL/outbox через `available_at`, с ограничением числа попыток и backoff; без бесконечных `requeue=true` циклов. DLQ используется для диагностики, а не как единственный источник terminal state.
- Attempts используют lease token и срок действия; terminal completion проверяет fencing token, чтобы поздний worker не перезаписал результат новой попытки. Recovery loop разбирает просроченные `processing` и готовые outbox entries. Дубликат delivery безопасен и не создаёт вторую terminal запись или повторное начисление метрик.
- В RabbitMQ находятся только идентификатор job и минимальные технические метаданные. Подтверждённая публикация может быть повторена после сбоя relay до фиксации outbox sent; consumer обязан быть идемпотентным.

### Данные, метрики и эксплуатационные решения

PostgreSQL хранит owner binding, idempotency key/digest, job state, attempts, lease, безопасные категории ошибки, канонический результат, timestamps и outbox. Изображение имеет непрозрачный сгенерированный ключ. Сначала файл записывается в приватный volume, затем в одной DB-транзакции сохраняются job и outbox; orphan files удаляются отдельной безопасной уборкой. При ошибке между file write и DB commit запрос не получает `202`.

Метрики Go разделяют принятые jobs, текущую очередь/возраст ожидания, попытки и повторы, время обработки, terminal outcomes, ошибки completion/relay, stale lease recovery, polling и использование file volume. Целевой механизм долговременного хранения этих агрегатов предстоит выбрать при проектировании deployment; текущий локальный state file не является job store. Счётчики не должны включать идентификаторы пользователей, image content/hash, распознанные значения или request-level историю. Успешная постановка не означает успешное распознавание; accepted/processing/completed/failed учитываются отдельно.

Для принятого job изображение должно оставаться доступным до завершения/восстановления обработки; после terminal decision запускается его удаление, а сбои уборки повторяются. Canonical result удаляется клиентским receipt ACK или спустя фиксированные 15 минут после terminal state. Технические tombstones пока не имеют срока удаления и требуют наблюдения за ростом БД. Допустимый deadline polling и public SLO не выбраны и не обещаются. Один-host volume, локальный Compose и восстановление после перезапуска не дают HA или защиты от потери самого хоста.

## Этапы и acceptance gates

Этапы выполняются по порядку; следующий этап начинается после прохождения gate предыдущего. Статус относится к плану, а не к существующим runtime возможностям.

### 1. Зафиксировать контракт и исходные ограничения — завершён: контракт и документация

**Результат:** этот план, согласованные изменения OpenAPI и документов результата/архитектуры/продукта; текущая sync операция явно отделена от новой async операции; новые endpoints, auth owner, idempotency replay/conflict и error/status semantics обозначены как planned.

**Acceptance:** OpenAPI и связанные документы одинаково описывают `202`, polling, четыре статуса, result/error envelope, `Idempotency-Key`, owner isolation и то, что реализация ещё не shipped. Текущий route по-прежнему `200`; в плане нет выдуманных числовых retention/deadline/limits.

**Проверка этапа:** OpenAPI 3.0.3 прошёл валидацию (84 references); четыре канонических примера совпадают с `API_RESULT.md` и проходят проверку формата ответа; lifecycle проверен на четырёх положительных и семи отрицательных случаях. Все существующие operations/components, включая sync recognition и `ErrorResponse`, остались без изменений относительно `HEAD`; `AsyncErrorResponse` изолирован в новом async контракте. Ссылки между локальными документами разрешаются, `git diff --check` прошёл. Проверялись только контракт и документация: runtime, интеграционные сценарии и нагрузка не запускались; новые endpoints и async runtime не реализованы.

### 2. Подготовить PostgreSQL, миграции и постоянное хранилище изображений — завершён: storage foundation

**Результат:** Compose foundations для PostgreSQL и RabbitMQ с readiness checks и persistent volumes; контролируемый запуск версионированных schema migrations; базовые таблицы job/attempt/outbox; отдельный приватный файловый volume и Go `internal/imagestore` foundation с непрозрачными ключами. Этот этап не добавляет HTTP intake, публикацию outbox, Go API/OCR consumer services в Compose или чтение изображений worker-ом. Состав конечного Compose окружения включает четыре приложения/инфраструктурных компонента, но на данном gate не требуется, чтобы все четыре уже запускались вместе.

**Acceptance:** чистое поднятие инфраструктуры ждёт readiness PostgreSQL/RabbitMQ; migration runner применяет schema контролируемо и повторный запуск не меняет уже актуальную схему; таблицы job/attempt/outbox и indexes/check constraints соответствуют модели. Реальный PostgreSQL container restart подтвердил сохранение schema и прямых test fixture записей job/outbox. Image store приватно сохраняет UUIDv4-key objects, sync-ит файл и директорию и после close/reopen читает те же bytes; проверки включают ограничения MIME/размера, no-overwrite, symlink/path traversal rejection, ownership/content-checked deletion и сбои file/directory/parent sync. Проверено локальное односерверное foundation; это не доказывает приём HTTP jobs или согласованность upload с DB transaction — это gate этапа 3. Python consumer ещё не подключён, поэтому его DB credential separation и read-only shared mount остаются acceptance следующих этапов. Это single-host foundation, не HA.

**Проверка этапа:** на Go 1.25 прошли `GOTOOLCHAIN=go1.25.0 go test ./... -count=1 -timeout=180s` (12 packages), `GOTOOLCHAIN=go1.25.0 go vet ./...`, форматирование Go-кода и scoped `git diff --check`. Изолированный Compose harness прошёл PostgreSQL concurrent migration/reapply, checksum drift rejection, schema/index и constraint cases (19 ожидаемых отказов с допустимыми lifecycle/owner/outbox fixtures), реальный Compose migration runner и restart persistence `jobs`/`outbox` rows. Image store прошёл package/race/vet проверки на Go 1.25 и 14 top-level tests в Linux/arm64 контейнере с UID 65532. Точные границы и ограничения приведены в [TESTING.md](TESTING.md), [IMAGE_STORAGE.md](IMAGE_STORAGE.md) и [POSTGRES_SCHEMA.md](POSTGRES_SCHEMA.md). Проверка не реализует/не подтверждает публичный `202`, atomic upload+job/outbox transaction, RabbitMQ publish/delivery, OCR consumer или full Go/OCR application Compose stack.

**Dependency correction:** первоначальная формулировка этого gate требовала четыре одновременно работающих Compose services, общую файловую точку Go/worker и end-to-end restart/recovery принятой API job. Infrastructure/schema restart и fixture job/attempt/outbox persistence в реальном PostgreSQL container, а также close/reopen persistence image bytes относятся к этапу 2. Durable `202` acceptance подтверждён на этапе 3; controlled application Compose wiring, worker permissions/shared mount, публикация outbox, OCR consumer execution и end-to-end recovery прошли этап 4. Production rollout и OCR quality acceptance остаются отдельными gates этапов 7–8.

### 3. Реализовать долговечный POST и idempotency — завершён

**Результат:** Go upload handler валидирует multipart/размер, получает owner из проверенного индивидуального bearer credential, считает digest точных image bytes и normalized media type, сохраняет изображение в приватном volume и одной PostgreSQL transaction фиксирует job + outbox. Только подтверждённый commit даёт `202`. Optional `async_jobs` config включает intake; без него новый POST отвечает `503`, а legacy sync route работает отдельно. Существующий per-file `max_upload_bytes` остаётся верхним пределом одного файла; async deployment дополнительно требует operator-set positive `max_stored_image_bytes`, который ограничивает суммарные logical bytes store. `max_concurrent_uploads` ограничивает одновременно активные intake операции, ожидающие запросы могут прерываться context; OCR concurrency/`429` sync semaphore к этому маршруту не применяется. Один API process является единственным writer для одного image root.

**Acceptance:** реальная PostgreSQL + filesystem + HTTP composition подтвердила exact `202` body/headers, owner из hash-only credential registry, idempotency и MIME conflicts, 50 same-key и 50 mixed-payload races, 100 distinct `202` submissions, auth/request/privacy rejections, replay при заполненной image quota, неизменность sync `200` и безопасные повторы после потерянного application acknowledgement/HTTP response. Реальный migration runner и PostgreSQL restart также прошли. Сбой/неопределённость commit не дают `202` и не удаляют image; только подтверждённый проигрыш idempotency race может удалить свой новый upload. Уборка проигравшего файла best-effort: при ошибке orphan остаётся учтённым в storage quota. Registry хранит только SHA-256 token hash и owner UUID в приватном файле; raw token не появляется в server config, логах, БД или Git. Gate закрыт для durable intake, не для OCR throughput, обработки очереди или готового client flow. `GET` status всё ещё этап 5; публикация outbox и OCR consumer — этап 4.

**Проверка этапа:** `GOTOOLCHAIN=go1.25.0 go test ./... -count=1 -timeout=180s` и `GOTOOLCHAIN=go1.25.0 go vet ./...` прошли. Это подтверждает реализованный HTTP/storage boundary; нагрузка настоящего OCR, queue execution, status polling и deployment full stack этим gate не проверялись.

**Legacy static credential provisioning:** `cmd/client-token -private-dir DIR [-owner-id UUID]` остаётся для ранее настроенных клиентов, перехода и восстановления доступа. Он создаёт raw token artifact и hash-only registry artifact вне checkout; новые Android установки не получают токен от администратора и не используют этот helper в штатной автоматической регистрации. Если включён `credentials_file`, static registry проверяется перед DB-backed enrolled credentials; запись регистрации, чей hash зарезервирован в static registry, отклоняется. Не отправляйте raw credential по недоверенной сети без TLS.

### 4. Подключить outbox relay, consumer lifecycle и recovery — завершён: controlled delivery/recovery acceptance

**Результат:** в коде есть Go outbox publisher с confirms и mandatory routing; durable RabbitMQ quorum work queue с single-active-consumer и `prefetch=1`; отдельный Python consumer с manual ACK; приватные claim/complete/fail/reject routes; attempts/lease/fencing; bounded DB-backed retries с `available_at`; terminal/retry DB decision перед ACK; recovery просроченных attempts и unpublished events. Для work queue отключён broker delivery limit, чтобы broker не DLQ-ил ещё валидный job до DB claim/recovery; DB attempt policy остаётся retry authority. Go остаётся единственным компонентом с доступом к PostgreSQL. Повторы после retry и lease recovery не гарантируют strict FIFO; quorum queue в текущем single-host deployment не означает multi-host HA. Этот этап не добавляет публичный GET и не завершает полноценный app Compose deployment.

**Acceptance:** bounded real PostgreSQL/RabbitMQ/Go/Python harness завершился с exit code 0 и 19 top-level invocations, включая семь lifecycle scenarios. Проверены duplicate publish/delivery, restart/recovery, retry exhaustion, lease expiry и late completion fencing. В ACK-loss case consumer завершился с кодом 73 после durable completion; RabbitMQ redelivered message, terminal callback ACK прошёл без второго OCR и без создания второй attempt/outbox row или изменения canonical result. Отдельная 20x lifecycle matrix прошла 20/20; детерминированная регрессия terminal timestamp прошла для completed, failed и poison-rejection переходов. Go 1.25 tests/vet/gofmt, Python 32 tests, Linux parent-death check и production image builds прошли. Queue profile не публикует host ports и является controlled integration, не production rollout: реальные private OCR weights/семантическое качество, TLS/ingress, HA, retention/deadline policy и полный operational rollout этим gate не проверялись. Public GET реализован на этапе 5; Android enrollment и polling приняты на этапе 6 через synthetic HTTP fixture.

### 5. Реализовать polling и безопасное чтение результата — завершён

**Результат:** owner-scoped read-only `GET /v1/passport/jobs/{job_id}` с четырьмя состояниями, terminal result/error, `Cache-Control: no-store`, одинаковым `404` для malformed/missing/foreign IDs и bounded database read. Регистрация ограничена операторскими cap values, direct-peer ACL и доступностью DB. Конфигурация `async_jobs.client_enrollment` включает её; при отсутствии блока route отвечает `503`. `credentials_file` становится необязательным только когда включён enrollment; прежние static hash credentials продолжают работать. ### 7. Закрыть эксплуатационные, security и privacy границы — принято

**Результат:** принята политика хранения без архивирования фотографий и распознанных результатов. Изображение удаляется сразу после terminal OCR decision; при ошибке удаления остаётся только до повторной успешной уборки. Канонический result удаляется после receipt ACK клиента либо через фиксированные 15 минут после terminal state. Job/idempotency tombstones и минимальные attempt/outbox fencing metadata остаются как техническая идемпотентность; они не содержат изображения или распознанный текст и могут расти без срока, поэтому требуются агрегатное наблюдение за ростом БД и контролируемая операторская политика.

Публичный `POST /v1/passport/jobs/{job_id}/receipt` доступен только владельцу: `204` означает, что receipt учтён или результат уже удалён; `409 job_not_terminal` означает, что job ещё выполняется; `404` одинаков для malformed, отсутствующего и чужого ID. После удаления result status GET возвращает `410 job_result_gone`, даже если периодическая уборка ещё не успела сработать. Повтор POST по прежнему idempotency key возвращает тот же job ID и не восстанавливает удалённое изображение или результат. `GET /healthz` — process liveness; внутренний `GET /readyz` требует PostgreSQL и доступного image root, но не RabbitMQ/consumer. Health probes не являются публичным API и остаются в private deployment network.

Database-enrolled client credentials are revoked with `cmd/client-admin revoke`; the hash row remains as a tombstone and cannot be reactivated. A legacy static-only credential is not a database installation, so the UUID command cannot revoke it: remove its registry entry and restart API instances. If the same hash must also be barred from future anonymous enrollment, persist it as a revoked database tombstone with `cmd/client-admin revoke-hash` using a private file containing only that SHA-256 hash; this operation does not require the raw token. When an async database lookup is configured, that revoked tombstone overrides any stale matching static entry. Active enrollment caps count only nonrevoked rows, while the per-minute admission cap continues counting new registrations, including revoked ones. There is no login, account, or recovery for the old identity: loss of Keystore means a new installation and client principal. Encrypted technical backups exclude image bytes, recognized fields/result payloads, raw bearer values, and image paths; they may include metadata such as caller-supplied idempotency keys, so archives remain sensitive and require private key/file handling. Clients must use random opaque keys without personal/document text. After image-volume loss, queued jobs whose files are missing require a new scan; a database backup cannot restore image/result payloads.

`async_jobs.retention` требует явные `claim_lease`, `interval` (не более 5 секунд), `operation_timeout` и `batch_size`; API повторяет неудачную файловую уборку. Не обещается физическое secure wipe или точный срок удаления при отказе диска/процесса. Bounded component checks подтвердили реальную PostgreSQL/filesystem retention, owner receipt и revocation/cap limits; `/readyz` проверяет PostgreSQL и image root, а aggregate-only `passport-ops snapshot` прошёл в Compose. Encrypted technical backup keygen/create/restore прошёл вместе с отказом для неправильного ключа и непустой target DB. Worker startup и AMQP readiness проверены без OCR inference. TLS configuration и trusted test-certificate rehearsal прошли, без активации production domain/certificate. Долговечная конфигурация была promoted в private `.local/async-runtime/candidate`; API cutover на `192.168.1.91:8080` за private Caddy принят после проверки остановки прежнего listener, start/status/stop и подготовки rollback manifest. Девять focused bridge tests прошли. Кандидатная проверка enrollment/replay/auth/revocation вернула ожидаемые `201`/`200`/`404`/`401`; старый `18080` listener остановлен. Health/worker/admin endpoints не публикуются через Caddy.

**Acceptance:** owner isolation сохраняется на receipt/status; terminal image cleanup и result expiry проверены реальной PostgreSQL и файловым хранилищем; повтор receipt безопасен; `410` выдаётся по durable marker и deadline независимо от janitor; отозванный token не работает и не переактивируется; активный enrollment cap исключает revoked rows, rate cap остаётся bounded; health readiness ждёт только DB+image root; snapshot содержит только агрегаты и threshold flags. Это не сервис доставки уведомлений: alert delivery, schedule и внешний мониторинг данным gate не подтверждены. Encrypted technical backup restore на пустую target DB и отказы для неверного ключа/непустой БД проверены; restore сохраняет только технические записи как failed/purged tombstones и не восстанавливает изображения, результаты или исполняемые попытки. Документированы последствия потери хоста и отсутствие payload backup. Обработка не имеет объявленного queued-job deadline или SLA; без consumer задания могут оставаться в очереди. TLS configuration и trusted test-certificate rehearsal прошли; production domain/certificate activation остаётся отдельной операционной задачей. LAN cutover на `8080` с durable runtime config, start/status/stop и rollback preparation проверен. Stage 7 принят; он не является capacity/реальным OCR acceptance — это этап 8.

Mock-only тест не доказывает OCR throughput. Без реальных измерений нет capacity claim; bounded результаты ниже относятся только к указанной конфигурации. Burst target не означает, что все jobs обрабатываются одновременно или завершаются к числовому deadline. Повторяются аварии API после file write/commit, relay после confirm, worker во время OCR, completion до ACK, перезапуск RabbitMQ/PostgreSQL и очистка файлов.

## Решения, оставленные открытыми

- TLS/ingress и внешний production rollout остаются операционными решениями; срок хранения результатов фиксирован в 15 минут после terminal state или до receipt ACK, а images удаляются после terminal OCR.
- Числовая per-file upload limit задаётся существующей конфигурацией; aggregate image-store quota обязательна в async config, но численное значение задаёт оператор. Наблюдение за бессрочными техническими idempotency/fencing tombstones и capacity thresholds настраивается оператором.
- Продолжительность и вид failure retry/backoff будут выбраны из наблюдаемой длительности настоящего OCR и требований продукта; план не задаёт чисел.
- Backup/restore оператора и доступность после полной потери single host; multi-host HA не входит в целевой объём.
- Порядок полного удаления старого sync endpoint должен совпасть с Android rollout; автоматическая смена его `200` на `202` исключена.
